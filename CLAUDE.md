# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is a mail gateway/router. It accepts inbound SMTP, applies routing rules to forward mail to configured relay targets, and POSTs structured JSON events to a companion logging service. The gateway is **`mailgw-go`**; the original [Haraka](https://haraka.github.io/) (Node.js) implementation is frozen under `legacy/`.

The repo is a monorepo with a private root `package.json`. **`webui-fastify/` and
the three `docs/*` sites are the pnpm workspace members** (see
`pnpm-workspace.yaml`); `logservice/`,
`tests/`, and `certs/` are standalone **Bun** packages with their own `bun.lock`,
deliberately kept out of the pnpm workspace so pnpm and Bun don't fight over
`node_modules`; `mailgw-go/` is a Go module.

**`legacy/` holds the frozen Haraka-era stack** — `legacy/mailgw/` (Haraka),
`legacy/webui-express/` (the Express UI), `legacy/deploy/` (its deployment),
`legacy/docs/` and `legacy/archive/`. The two packages there are Node/pnpm but
are **deliberately not workspace members**, so a root `pnpm install` ignores
them; install one on its own with `cd legacy/mailgw && pnpm install`. Prefer
changing the modern stack — touch `legacy/` only to keep it building.
- **`legacy/mailgw/`** — the Haraka SMTP server with custom plugins (`legacy/mailgw/plugins/`); frozen
- **`mailgw-go/`** — a **Go** rewrite of the Haraka gateway (`emersion/go-smtp`), and **now the gateway the compose stacks run** (it owns port 25; the Haraka service is commented out in `docker-compose.yaml`). Its own Go module, deliberately **not** a pnpm workspace member (same precedent as `logservice/` and `tests/`). Adds a declarative routing/policy rule engine, per-recipient routing and a durable outbound queue. **M1–M16 are all done.** Central management (M3–M6: the console half in `webui-fastify`, the gateway half — identity + wizard, config pull, versioned apply and rollback, fleet observability), the outbound queue (M7: bounces, `mailq`, quarantine release, MX, connection reuse, ordered shutdown), and **parity hardening** (M8: attachment MD5 scanning, inbound STARTTLS and implicit TLS, and a replayer for spilled audit events) — **so Haraka can now be retired rather than kept alongside.** M9–M11 are defect and hardening passes from two audits: SMTP and delivery-path correctness (M10) and **resource bounds** (M11 — the inbound connection cap, a bounded config-bundle decode, cache eviction, and cancellation reaching a pooled relay connection). **M16 is the re-audit of M11's own code**, run before it was committed: twelve defects, the worst being that M11's connection cap wrapped the accepted connection and so hid the `*tls.Conn` from go-smtp — costing an `implicit_tls` listener its TLS identity *and* the only pre-handshake read deadline, so a silent peer held its semaphore slot for ever. **M12 closed the security item that headed the backlog**: the always-listening admin UI is now behind a first-boot claim code, a database-backed session and a CSRF token, and `/metrics`/`/readyz` behind an optional bearer token that travels in the bundle. **M13 gave the gateway an inbound authorization gate that is not an IP address** — `AUTH PLAIN`/`AUTH LOGIN` against bcrypt hashes the console issues, plus inbound RFC 3461 DSN honoured end to end. **M14 gave it an opinion about who a message is from**: SPF, DKIM and DMARC verified inbound and recorded in an `Authentication-Results` header, DKIM signing outbound from keys on the gateway's own disk, and every result a rule field rather than a config boolean — so "reject on DMARC fail" is something an operator writes, and nothing is refused that was not refused before. **M15 finished the pair M11 started** — `max.connections` bounds how many connections exist at once, rate limits bound how often anything happens at all (per IP, per sender, per user, per recipient domain, per failed AUTH), every one off by default and every refusal a 4xx. **The shipped node is zero-configuration**: no env vars, no CLI args, no config files. **Milestone plans live in `plans/`** — one file per milestone (`M<n>-<title>.md`), status on line 3, indexed in `plans/README.md`; `mailgw-go/TODO.md` is now just that index plus the non-milestone backlog. Milestone numbers are identity — never reused, never renumbered — so running order lives in the index, not in the number (**M9** is defect fixes from the 2026-07-29 review and was worked first; M9.4 landed with M4, M9.5 with M7). See its section below.
- **`logservice/`** — a Bun HTTP API (`Bun.serve`) that receives events from the plugins and stores them in MariaDB via Bun's native SQL client (`Bun.SQL`, MySQL adapter); written in TypeScript
- **`webui-fastify/`** — the **active** admin web UI (Fastify + Drizzle, Node/pnpm): log viewers, relay/relay-group config, session login, and the **Central Management** server for mailgw-go gateways (inventory, approval, config profiles, versioned deploy/rollback, `/agent/*` machine API). Native HTTP/2, pug-only. Its log-viewer reads **proxy to logservice** (it no longer queries the log tables directly); the build/compose stack ships this image. See its section below.
- **`legacy/webui-express/`** — the **legacy** Express rewrite target, kept as a reference. Same product on Express 5 over HTTP/1.1. It still carries the pre-refactor baggage `webui-fastify` shed (dual pug/ejs engines, the experimental Deno adapter, the full duplicated model set, and the overlapping `/api` ingest + `/filter/md5` endpoints). Prefer changing `webui-fastify`.
- **`docs/`** — three **VitePress** documentation sites, each its own pnpm workspace member: `docs/public/` (customer-facing: what the gateway does, configuration, the rule DSL, operations), `docs/internal/` (engineering: architecture, conventions, standing decisions, known gaps), `docs/testing/` (ten manual test plans with preconditions, numbered steps and expected results, plus a release checklist). `pnpm docs:public:dev` / `docs:internal:dev` / `docs:testing:dev` on ports 5173/5174/5175; `pnpm docs:build` builds all three. The split is an **audience boundary and it is load-bearing**: milestone plans, audit findings and defect histories must not land in `docs/public/`. **`plans/`, both `TODO.md` files, `CLAUDE.md`, `deploy/README.md` and `logservice/docs/api.md` are deliberately NOT copied into any site** — they are living files other files cross-reference by relative path, so `docs/internal/` links to them and covers what they do not. Note the three builds are separate, so a relative link from one site into another is a dead link and fails the build. See `docs/README.md`.
- **`tests/`** — cross-cutting end-to-end tests (Bun): logservice API (`tests/api/`) and SMTP pipeline (`tests/smtp/`)
- **`certs/`** — a Bun CLI that generates self-signed TLS certs from a JSON config (`node-forge`); produces the certs the webui serves over TLS

### mailgw-go (the gateway)

A standalone **Go module** (`github.com/ngmaibulat/mailgw/mailgw-go`), not in the pnpm workspace. No build step beyond `go build`; no code generation.

```bash
cd mailgw-go
go build ./... && go vet ./... && go test -race ./...
go run ./cmd/mailgw-go check -config ./testdata/config   # validate config, non-zero on error
go run ./cmd/mailgw-go serve -config ./testdata/config   # run (listens on 2525)
go run ./cmd/mailgw-go fields                            # list every matchable rule field
go run ./cmd/mailgw-go explain -config ./testdata/config --ip 10.20.0.5 --from a@x.com --rcpt b@ngm.dev
go run ./cmd/mailgw-go convert-routing config/routing.json > config/routing.yaml
go run ./cmd/mailgw-go mailq -config ./testdata/config          # list the outbound queue
go run ./cmd/mailgw-go mailq release -config ./config <uuid>    # quarantine -> queue
go run ./cmd/mailgw-go events -config ./testdata/config         # audit events logservice refused
go run ./cmd/mailgw-go events replay -config ./testdata/config  # resend them now
go run ./cmd/mailgw-go config show -data /var/lib/mailgw-go   # the cached bundle, secrets redacted
go run ./cmd/mailgw-go claim status -data /var/lib/mailgw-go  # the admin UI's claim code
go run ./cmd/mailgw-go claim reset  -data /var/lib/mailgw-go  # rotate it, sign everybody out
go run ./cmd/mailgw-go check -data /var/lib/mailgw-go         # validate what a managed node is running
pnpm test:mailgw-go                                      # from the repo root
./bump.sh && ./container-build.sh                        # version bump is SEPARATE from the build
```

> **It is now the gateway in compose.** `docker-compose.yaml` maps host `25` → container `2525` for `mailgw-go` (the image runs as uid 65532 and cannot bind a privileged port) and keeps `2525:2525` published so `pnpm test:e2e:smtp:go` still works; the Haraka `mailgw` service is **commented out**, not deleted — uncomment it and move mailgw-go off host 25 for a parity run. `deploy/gateway/docker-compose.yaml` (the production edge node) likewise runs mailgw-go, keeping `network_mode: host` so the IP allowlist sees real client addresses, with `user: "0:0"` because a nonroot uid cannot bind 25 and per-container sysctls are refused under host networking; it is **zero-configuration** and pins nothing, so its `server.yaml` — listening on `0.0.0.0:25` — is a `server` profile deployed from the console rather than a file on the host. Standalone (`go run ... serve`) it still listens on 2525. Both gateways post to the same logservice; their uuid spaces are disjoint and mailgw-go stamps `X-NGM-Gateway: go` on relayed mail. Reuses `relays.json`, `ngmfilter.json`, `logging.json` and `routing.json` **unchanged**; `server.yaml` replaces `connection.ini`/`smtp.ini`/`log.ini`/`me`/`smtpgreeting`/`host_list`, `admin.json` (M12, optional) holds the `/metrics` bearer token, and `auth.json` (M13, optional) the inbound SMTP AUTH credentials as bcrypt hashes. Rules come from `routing.yaml` when present, otherwise `routing.json` is transpiled — `mailgw-go/config/` ships only the JSON and `mailgw-go/testdata/config/` ships a worked YAML, so CI covers both. `SIGHUP` reloads the allowlist **and** the rules, all or nothing, keeping the running configuration if the new one fails validation — "re-read the files" in file mode, "re-apply from the cache" in managed mode. Unlike the Node container scripts, `container-build.sh` does **not** bump the version — use `./bump.sh`.

### webui-fastify (active admin UI)

A pnpm workspace member (`mailgw-webui-fastify`). The root `pnpm webui*` scripts target it:

```bash
pnpm webui:dev                             # nodemon (auto-reload)  → src/index.ts  (alias for pnpm --filter mailgw-webui-fastify)
pnpm webui:start                           # node src/index.ts (production)
pnpm webui dev                             # same as webui:dev (the `webui` alias forwards args)

pnpm --filter mailgw-webui-fastify lint       # biome lint
pnpm --filter mailgw-webui-fastify check      # biome check (lint + format check, no write)
pnpm --filter mailgw-webui-fastify check:fix  # biome check --write (apply safe fixes + format)
cd webui-fastify && node create_user.ts <email> <password>   # seed a login user
```

> Written in **TypeScript** (`.ts`) and run directly by Node 26 via native type-stripping — **no build step / no emit**; `tsconfig.json` is for IntelliSense + `pnpm typecheck` only (`typescript` is a devDep, not needed at runtime, so the prod Docker image omits it). Source uses `verbatimModuleSyntax` + `erasableSyntaxOnly`, so relative imports carry the real `.ts` extension (`import { build } from "./app.ts"`). Lint + format is **Biome** (`biome.json`, recommended rules; 4-space / double-quote / 80-col / semicolons to match the old `.editorconfig`). Biome scopes to `src`/`db`/root `*.ts`/`*.json` (vendored `public/lib` and browser `public/js` are excluded); its import-sorting assist is **off** so the node/third-party/local import grouping is preserved. Unused Fastify handler params follow the `_`-prefix convention. Serves **native HTTP/2** (Fastify `{ http2: true, https: { allowHTTP1: true } }`) and reads `./certs/server.{key,crt}` (relative to its working dir) on boot — it will crash without those certs. Generate them with the `certs/` project (see below); locally a `certs` symlink points at `certs/generated/webui`, and in Docker the same dir is mounted. Templates are **pug-only** (`TEMPLATE_DIR`, default `./templates/pug`). Log-viewer reads proxy to logservice via `LOGSERVICE_URL` (default `http://localhost:3000`) + optional `LOGSERVICE_API_KEY` (sent as `X-API-Key`).

Each Node/Bun service has `container-build.sh` (local `--load`) and

```bash
./webui-fastify/container-build.sh           # ACTIVE webui image (ngmaibulat/mailgw-webui-fastify, node:26-alpine, root context)
./logservice/container-build.sh              # logservice image (oven/bun-alpine, own-dir context)
./mailgw-go/container-build.sh               # gateway image (distroless/static, own-dir context)
./legacy/mailgw/container-build.sh           # legacy Haraka image (node:26-alpine, -f legacy/mailgw/Dockerfile, root context)
cd legacy/mailgw && ./container-dev.sh       # run latest legacy image locally (mounts its plugins live)
./legacy/webui-express/container-build.sh    # legacy Express webui image (ngmaibulat/mailgw-webui)
pnpm run docker:push               # push the NEW stack: mailgw-go + logservice + webui-fastify
pnpm build:containers              # docker:push + the legacy Haraka image
docker compose up                  # full stack: mariadb + db-migrator + logservice + mailgw-go + webui + mailhog
docker compose run --rm db-migrator   # apply SQL migrations against MariaDB (runs `bun src/dbmigrate.ts`)
```

> **`pnpm run docker:push` is the release command for the newer solution** — `mailgw-go` +
> `logservice` + `webui-fastify`, the three images a modern deployment actually runs. It bumps
> all three versions first: `logservice`/`webui-fastify` bump inside their own `container-push.sh`,
> and it calls `mailgw-go/bump.sh` explicitly because that script's push deliberately never mutates
> the tree. The steps are `&&`-chained, so a failed build aborts the rest rather than leaving a
> half-pushed `:latest`. Legacy `mailgw` (Haraka) and `webui-express` are **not** included — use
> `pnpm build:containers` or the per-package scripts for those.

> **`docker-compose.yaml`'s `webui` service runs the `mailgw-webui-fastify` image** (with `LOGSERVICE_URL`/`LOGSERVICE_API_KEY` wired for the read proxy). The root `pnpm build:webui` / `build:containers` scripts build/push that same Fastify image. The legacy Express image (`ngmaibulat/mailgw-webui`) is built only via `./legacy/webui-express/container-build.sh`.

> Before `docker compose up`, generate the webui TLS certs (`pnpm certs`) — the
> `webui` service mounts `certs/generated/webui` and won't start without them.

### Deployment (`deploy/`)

The root `docker-compose.yaml` is the **dev** stack (everything on one host,
mailhog, throwaway passwords). Production lives in `deploy/`, split by role:

- **`deploy/core/`** — one per install: mariadb + logservice + webui-fastify.

  `upgrade.sh` pulls new images and re-runs migrations. `CORE_HOST` in `.env` is
  the address **edge nodes** use — it becomes `GATEWAY_LOGSERVICE_URL`, so

  compose file has no `command:`, no `environment:` and no config mount, only

  (real client IPs for the allowlist; a nonroot uid cannot bind 25). Numbered
  scripts `00`→`05`; `04-gateway.sh` takes **no arguments** — it pulls, starts,
  and prints the wizard URL **and the claim code** (read out of the container
  with a bounded retry, since `up -d` returns before the process opens its
  store). The node does not relay until an operator signs in with that code,
  registers it, approves its fingerprint and deploys a configuration.
  **`05-firewall.sh` is still required, not optional** even now that M12
  authenticates the UI: it is always listening on a root process on an
  internet-facing host, and what a signed-in caller can do is re-point the

  cache) is the thing to back up — losing it makes the node a stranger.

`legacy/deploy/` is the frozen Haraka-era equivalent (`core/` + `mailgw/`, no

## Architecture

### Haraka plugin pipeline

Haraka loads plugins listed in `legacy/mailgw/config/plugins` and calls registered hooks at each SMTP stage. All custom plugins live in `legacy/mailgw/plugins/` and follow the `np` naming prefix:

| Plugin | Hook(s) | Purpose |
|---|---|---|
| `npRoute.js` | `hook_get_mx` | Route outbound mail via `RoutingTable` |
| `npFilter.js` | `hook_connect`, `hook_rcpt`, `hook_queue_outbound` | IP allowlist enforcement (plus local rcpt logging) |
| `npConnection.js` | `hook_connect` | Write connection info to a local log file + IP-blacklist placeholder (does **not** POST to logservice) |
| `npData.js` | `hook_data` | POST connection info → logservice (`url_conn`) |
| `npQueue.js` | `hook_queue_outbound` | POST transaction/queue event → logservice (`url_queue`) |
| `npLogDelivery.js` | `hook_delivered` | POST delivery outcome → logservice (`url_delivery`) |
| `npFilterAttach.js` | `hook_data_post` | Attachment MD5 blocklist check via POST `/filter/md5`; also POSTs connection + transaction events |

The logservice-posting plugins `npData`, `npQueue`, and `npLogDelivery` read endpoint URLs (`url_conn` / `url_queue` / `url_delivery`) from `legacy/mailgw/config/logging.json` via Haraka's `this.config.get`, and POST JSON through `legacy/mailgw/plugins/functions.js#postWithLogging` (which writes a local log line, then calls `httplog`). Note that `npFilterAttach` instead uses **hardcoded** `http://localhost:3000` URLs.

#### Plugin inconsistencies & gotchas

The plugin set grew organically and is **not** uniform — don't assume symmetry. Known quirks (improvement items tracked in `legacy/mailgw/TODO.md`):

- **Name ≠ behavior.** `npConnection` does *not* POST to logservice — it only writes a local log file and has a dead `isBlacklistedIP()` placeholder (always `false`). The plugin that actually sends connection info to the API is `npData`, at the `hook_data` stage, posting to `url_conn`.
- **Config source split.** `npData` / `npQueue` / `npLogDelivery` resolve URLs from `logging.json`; `npFilterAttach` **hardcodes** `http://localhost:3000`, so its calls only work when logservice is co-located (e.g. they break in Docker where logservice is a separate host).
- **Overlapping event posting.** `npFilterAttach.hook_data_post` *also* posts connection (`url_conn`) and transaction (`url_queue`) events in addition to its MD5 check, overlapping `npData` / `npQueue` — a duplicate-row risk (the "no longer double-insert" note in `logservice/src/routes/api.ts` is a scar from this).
- **Posts are fire-and-forget.** `postWithLogging` / `httplog` don't `await` the POST; failures are only logged, never retried or surfaced to the SMTP transaction.
- **Plugins that never touch the API:** `npConnection` (local file), `npFilter` (IP allowlist; its `hook_queue_outbound` only logs rcpt locally), `npRoute` (routing; DEV-only local log).

### Routing logic (`legacy/mailgw/plugins/Route.js`, `legacy/mailgw/plugins/RoutingTable.js`)

On `register`, `npRoute.js` loads two config files and builds a `RoutingTable`:
- `legacy/mailgw/config/routing.json` — array of route rules, each specifying `relay`, `sender`, `sender_domain`, `rcpt`, `rcpt_domain` (empty string = wildcard)
- `legacy/mailgw/config/relays.json` — map of relay name → relay object (host, port, etc.)

On `hook_get_mx`, `RoutingTable.findRoute(sender, rcpt)` walks the rules in order and returns the first matching relay.

### Runtime config files (not in repo, mounted at `/opt/mailgw/config`)

- `connection.ini` — required Haraka connection settings
- `routing.json` — route rules
- `relays.json` — relay definitions
- `logging.json` — logservice endpoint URLs (`url_conn`, `url_queue`, `url_delivery`)
- `ngmfilter.json` — IP allowlist `{ "allowed": ["127.0.0.1", ...] }`

### logservice

`Bun.serve` app (`logservice/src/index.ts`) listening on `PORT` (default 3000). Routes:
- `GET  /` — health check, returns `{ status: "OK" }`
- `POST /api/connection` — inbound connection events; `GET /api/connection` — search
- `POST /api/queue` — queue events (stored as `Transaction` rows)
- `POST /api/delivery` — delivery events (validated with a Zod schema); `GET /api/delivery` — search
- `GET  /api/transaction` — search transactions
- `GET  /api/hashlookup` — search attachment MD5 lookups; `HashLookups` LEFT JOIN `Transaction` (on `txn_uuid = uuid`) so each row carries its message's `sender`/`rcpt_list`/`dt` (`searchHashlookup` in `src/query/search.ts`). Only `HashLookups` columns are searchable
- `POST /filter/md5` — attachment MD5 blocklist check, returns `{ action: "allow" | "block" }`

Each handler is wrapped by `handle()` = `withAuth(withErrorHandling(...))` (`src/middleware/`). Auth checks the `X-API-Key` header against `API_KEY`; when `API_KEY` is unset, all requests are accepted. The `GET` search endpoints take a JSON `q` query param (`{ search: [{ field, operator, value }], searchLogic, sort: [{ field, direction }], limit, offset }`) parsed/whitelisted in `src/query/`. `buildWhere` takes an optional `tablePrefix` to qualify columns for JOIN queries (used by the hashlookup search); `buildOrderBy` builds a whitelisted `ORDER BY` (field checked against the same allowlist, direction normalised to `ASC`/`DESC`, default `DESC`, fallback `id DESC` when unsorted). Each search returns the real `total` matching-row count (a `COUNT(*)` over the same WHERE), not just the page size, so clients can paginate.

**The log tables carry a `gateway` column** (migration `023`, indexed), and `Delivery` additionally a `route_rule` — which gateway wrote the row, and which routing rule sent that recipient there. Both are **optional** on the wire and NULL for anything written earlier; `schemaDelivery` accepts them, and `toConnectionRow`/`toTransactionRow` map them (those two endpoints validate nothing by design). The three field allowlists in `src/query/search.ts` are now **exported** so a unit test can assert membership without a database — that matters because `buildWhere` **silently skips** a field it does not recognise, so a column added to a table and a grid but forgotten there yields a filter that appears to work and returns every row. `GatewayMetrics` (migration `024`) holds the latest counter snapshot per gateway as JSON — deliberately a snapshot, not a time series. `Relays.use_mx` (migration `025`) resolves a relay's `host` as a domain via MX at delivery time; it defaults to 0 and `bundle.ts` omits it when false, so no existing configuration changes shape or digest. `CredentialSets`/`SmtpCredentials` (migration `026`, plus `GatewayAssignments.credential_set_id`) hold M13's inbound SMTP AUTH logins — **bcrypt hashes, not ciphertext**, which is the one place this is better off than `Relays.auth_pass`: the gateway only ever *verifies* an inbound credential, so `src/central/secrets.ts` is not involved and no key exists anywhere for a leaked bundle to be decrypted with.

Data access uses raw SQL via Bun's `Bun.SQL` (`src/db.ts`, MySQL adapter) — there is **no ORM**. Per-table query helpers live in `src/models/` (`connection.ts`, `transaction.ts`, `delivery.ts`, etc.). Schema migrations are plain numbered `.sql` files in `logservice/migrations/`, applied in order by the custom runner `src/dbmigrate.ts` (tracks applied files in a `_migrations` table). Migrations run via the `db-migrator` container, the `--migrate` boot flag (`index.ts`), or `bun run db:migrate`.

### webui-fastify (active admin UI)

Fastify app (`webui-fastify/src/app.ts#build()`, started over native HTTP/2 by `src/index.ts`). **TypeScript ESM throughout (`.ts`)**, run directly via Node's native type-stripping (no build step — see the webui-fastify command section above). Composition:
- **Plugins** registered at the root (inherited by all routes): `@fastify/formbody` (urlencoded), `@fastify/cookie` (signed, via `SIGN_COOKIE`), `@fastify/view` (pug), `@fastify/static` (`public/`, `index:false` so the dashboard owns `/`).
- **Encapsulation = the auth boundary.** Three nested scopes: (1) root — static assets, public & unlogged; (2) a "logged" child that adds the `logger` `onRequest` hook and the public auth routes (`/login`, `/logout`, `/profile`); (3) a "secured" child inside it that adds the `checkSession` `preHandler` hook, then registers the protected routes. Hooks only apply to their own scope + descendants, so static stays unlogged and auth routes stay ungated — replacing Express's ordering-dependent `app.use()` chain. The **`/agent/*` machine API is a fourth sibling at the root scope**, deliberately outside both the cookie gate (a gateway must not be redirected to `/login`) and the audit-log hook (a polling fleet would flood `Logs`); it brings its own Ed25519 signature `preHandler`.
- **Request-audit log scope (deliberate).** The `logger` `onRequest` hook (`src/middleware/logger.ts`) writes one row per request to the `logs` table, but `isNoise()` **intentionally skips `/favicon.ico` and the high-frequency `GET /api/*` grid reads** — the AG Grid log viewers fetch pages against `/api/*`, and auditing those reads would flood the table for no audit value. We **deliberately do not audit API read calls**; page navigation and config mutations (`POST /config/*`) are still recorded. Narrow `isNoise()` if read-access auditing is ever needed. This is separate from **Fastify's built-in pino request logging**, which `src/index.ts` enables only when `NODE_ENV != "production"` (level via `LOG_LEVEL`, default `info`; pretty-printed in dev via the `pino-pretty` transport — a devDep absent from the prod image, which never enables the logger anyway) — prod runs `logger:false` and relies on the DB audit trail above.
- **Routes** (`src/routes/`): `root` (dashboard), `log` (viewer pages), `api` (`/api/{connection,delivery,queue,hashlookups}` — **read-only**, proxied), `config-relay` (`/config/relay/*`, `/config/relaygrp/*`, `/config/profiles/*` CRUD; `/config/routing` now **redirects** to `/config/profiles`), `gateways` (`/gateways*`), and the root-scope `agent` (`/agent/*`). There is **no ingest API and no `/filter/md5`** — those live in logservice.
- **Central Management** (`src/routes/agent.ts`, `src/agent/verify.ts`, `src/central/bundle.ts`, `src/controllers/Ctrl{Gateway,Profile}.ts`). A mailgw-go instance generates an **Ed25519 keypair on first boot** and registers itself; **registration is open and there are no tokens**, so the row lands `status='pending'` and an operator approves a **fingerprint** (SHA-256 of the raw public key, hex). Every later request is signed over `METHOD\nurl\nunix-seconds\nsha256(rawBody)` with a 300s skew window; the scope registers its own raw-body content-type parser so the signature covers the exact bytes sent. Routes: `POST /agent/register` (self-signed, proves key possession, idempotent per fingerprint and **can never reset an approval**), `GET /agent/status` (answers a pending gateway too — that is how it learns it is waiting), `GET /agent/config` (**403 unless approved** — the one route approval gates), `POST /agent/report` (applied version, `apply_error`, `restart_required`, metrics), and **`GET /agent/ws`** — a WebSocket (`@fastify/websocket`) inside the same signed scope, so the upgrade is authenticated by the same signature. It exists so a deploy reaches a gateway in milliseconds rather than on its 15s poll; frames carry no state, and the gateway re-asks `/agent/status`. `deployBundle`, `rollbackTo` and `setStatus` publish to an in-process bus (`src/central/notify.ts`) **after** their transaction commits; because a second replica's deploy would not reach that bus, each live socket also re-reads its own gateway row every 10s. Deliberately not a message broker — the gateway's poll is doing the same job underneath. Config is modelled as **reusable profiles** (`ConfigProfiles`, kinds `ruleset`/`allowlist`/`server`, storing the raw file text) plus assigned **relay groups**; **Deploy** composes them into an immutable `ConfigVersions` row and points `Gateways.desired_version_id` at it, and **rollback repoints at an older row rather than minting a new bundle**, so what runs afterwards is byte-identical. Redeploying an unchanged config re-points instead of piling up versions (digest comparison over a depth-sorted stable stringify). **The rule DSL is validated by Go, not here** — the console does shape checks only; the gateway compiles on pull, keeps its last-good config, and reports `apply_error` back. Bundle keys mirror the config-directory files exactly (`server.yaml`, `routing.yaml`, `ngmfilter.json`, `relays.json`, `logging.json`, since M12 `admin.json` and since M13 `auth.json`), and `bundle.ts` is the single place handling the shape mismatches: relay-group name is the **top-level key**, `Relays.host` → `exchange`, port INT → number. `GATEWAY_LOGSERVICE_URL` / `GATEWAY_LOGSERVICE_API_KEY` (falling back to `LOGSERVICE_URL` / `LOGSERVICE_API_KEY`) are the logservice URL and key written into bundles — deliberately separate, because the webui's own container-internal URL and credential may not be what a remote gateway should use. **Because a managed gateway has no environment of its own, anything it used to read from one now travels in the bundle**: `logging.api_key`, `allowlist.allow_all` (passed through rather than stripped — without it an allow-all gateway could not be expressed from the console at all), per-relay `tls` / `allow_insecure_auth` / `auth_pass_env` (migration `022`), M12's `admin.metrics_token` (from `GATEWAY_METRICS_TOKEN`, infrastructure rather than per-gateway policy, on the `loggingEndpoints()` precedent), and M13's `auth.users` (from an assigned credential set, sorted by username because `stableStringify` deliberately does not sort arrays). Every optional field is **omitted when empty**, so an unchanged configuration keeps hashing identically — and `src/central/bundle.test.ts` finally pins that, the file having had no test at all before M13 added a key to it.
- **Fleet observability (M6).** `POST /agent/report` **persists** the metrics object it used to validate and discard, upserting `GatewayMetrics` (one row per gateway, keyed on `gateway_id`) inside the same transaction as the `Gateways` update — so a row can never carry a `last_seen` newer than the snapshot beside it. `AgentMetrics` (`src/validation/agent.ts`) is now bounded on every axis (≤128 keys, ≤64-char keys, finite non-negative integers) because the value is written rather than echoed. **`src/central/fleet.ts` is the single source of fleet vocabulary** — `STALE_AFTER_MS` is three poll intervals (45s; one missed poll is normal and flagging it would make the view cry wolf), `metricsFor()` parses snapshots best-effort per row so one malformed blob cannot take a page down, and `summarize()` builds what the dashboard card renders. Both `/` and `/gateways` read it, so they cannot disagree about what "stale" means. Staleness is only computed for **approved** gateways: a rejected one is silent by design. The dashboard card leads with pending approvals — the one fleet state that cannot resolve without a person — and every alert row links at the gateway it is about. The grids gained a **Gateway** column (all three) and a hidden **Route rule** (delivery); `src/routes/api.ts` needed no change, since the proxy forwards verbatim and logservice owns the field allowlist.
- **`auth_pass` is encrypted at rest** (`src/central/secrets.ts`): AES-256-GCM, key from `CONFIG_SECRET_KEY`, stored as `v1:<base64>`. The **console decrypts** when composing a bundle, so no key ever reaches a gateway — shipping ciphertext instead would make the key a fleet-wide shared secret held on internet-facing relays, which is strictly worse. A stored value with no `v1:` prefix is pre-migration plaintext and is read as such, so an install that never sets a key behaves exactly as before and rows migrate as they are re-saved. Wrong key or tampered ciphertext **throws** rather than yielding `""`, which would send a gateway out to authenticate with an empty password.
- **This gives `Relays`/`RelayGroups` their first consumer.** Those rows were previously a write-only sink. They now feed the composed gateway bundle — but only for **mailgw-go**, and only once the gateway-side pull lands (mailgw-go M5). **Haraka is unchanged and is now explicitly the legacy gateway**: it still routes purely from `legacy/mailgw/config/{relays,routing}.json` on disk, nothing under `legacy/mailgw/` opens a DB connection, and the old "DB → Haraka config bridge" epic is **closed as superseded** in `webui-fastify/TODO.md`.
- **Read proxy** (`src/routes/api.ts` + `src/logservice.ts`): the `/api/*` GETs validate the frontend's `?request=<json>` against a zod v4 schema (`src/validation/search.ts`, mirrors logservice's accepted shape — bad payload → **400**, unknown keys stripped), then forward it as logservice's `?q=<json>` and pass the response through verbatim (identical `{status,total,records}` shape). Path remaps: `queue` → logservice `/api/transaction`, `hashlookups` → `/api/hashlookup`. The webui **does not query the log tables directly**. On failure `logservice.ts` throws a typed `LogserviceError` (`kind: "upstream" | "network"`) that `api.ts` maps to **502** (logservice answered non-2xx) / **504** (unreachable or invalid JSON) — not a blanket 500; there is still **no fetch timeout** (TODO).
- **Auth** (`src/auth/`): session login (`bcryptjs` vs `User.hash`), `/login` `/logout` `/profile`. Sessions are **database-backed** (`Sessions` table, migration 021) via `src/globals.ts`, which exposes an async `SessionStore` — `setSessionStore()` swaps in a Map so `app.inject()` tests run without a DB. A restart no longer logs everyone out and >1 replica works. `checkSession` unsigns the cookie via `request.unsignCookie`. **Roles**: `Users.role` is `admin` | `viewer` (migration 020, existing rows promoted to `admin` so an upgrade can't lock the operator out); `requireAdmin` (`src/auth/roles.ts`) gates gateway approval, deploy/rollback and every config mutation. `/setup` and `create_user.ts` create **admins**.
- **Data**: **Drizzle ORM** (MariaDB via `mysql2`), **scoped to only what the webui owns** — `users`, `relays`, `relayGroups`, `logs`, `exceptions`, `sessions`, and the Central Management tables `gateways`, `configProfiles`, `gatewayAssignments`, `configVersions`, `configDeployments` (`db/schema.ts`). The webui **does not own/migrate this schema** — logservice's SQL migrations create the tables; `db/schema.ts` just describes the columns to query (no `drizzle-kit`/DDL here). `db/index.ts` exports the `db` instance (lazy `mysql2` pool, no import-time connect) + the table refs + `assertDbConnection()` (pinged at startup in `src/index.ts`). `src/adapter.ts` is now just a tiny re-export of uuid/bcrypt.
- **Config validation**: `src/validation/config.ts` uses **drizzle-zod** (`createInsertSchema`) to derive relay/relaygroup insert schemas from the Drizzle tables, `.pick()`ed to form fields (prevents mass-assignment) and `.extend()`ed to require `name`/`host`. The whole app is on **zod v4** — imported from `zod/v4` (the v4 entrypoint shipped by zod 3.25+), which is also what drizzle-zod 0.8 emits, so schemas and hand-written validators (`src/validation/{config,login}.ts`) all use one zod. Relay edit uses a "leave blank to keep" rule so editing never wipes the stored `auth_pass`. `parseProfileBody` additionally checks that an `allowlist` profile really is `{"allowed": [...]}` JSON — a body that isn't would fail-close the gateway on deploy.

### mailgw-go (Go rewrite of the Haraka gateway)

Built on `emersion/go-smtp` v0.24.0. Single binary, everything under `internal/`.

**Why it exists.** Two limits of the plugin set: routing was four fields and one operator (`Route.js:44` — case-insensitive equality, ANDed, so `ngm.dev` does not match `mail.ngm.dev`), and `npRoute.js:55` routed the whole message by `rcpt_to[0]`. Separately, delivery events were being lost: `npLogDelivery.js:37` sends `rcpt_accepted` as a comma-joined list where logservice validates a single address, so every multi-recipient delivery 400'd — invisibly, because the POST is fire-and-forget with no `response.ok` check (`functions.js:91`).

**How Haraka's hooks map:**

| Haraka | mailgw-go |
|---|---|
| `hook_connect` deny (`npFilter.js:49`) | a `net.Listener` wrapper (`internal/smtpsrv/listener.go`) — go-smtp calls `NewSession` at EHLO, so denying *before* the banner has to happen in front of the server |
| `hook_rcpt` (`npFilter.js:73`, accepts all) | `Session.Rcpt` — rcpt-stage policy, then a tentative `Route`; with no rule saying otherwise the behaviour is unchanged and the IP allowlist remains the only gate |
| `hook_data` (`npData.js:9`) | start of `Session.Data` — posts `/api/connection`, same timing; since M10 also from `Logout` when DATA was never reached, and from `Backend.NewSession` when the greeting is refused |
| `hook_queue_outbound` (`npQueue.js:9`) | `queue.Enqueue` — posts `/api/queue`, writes envelopes |
| `hook_get_mx` (`npRoute.js:48`) | `ruleset.Route` + `relays.Table.Lookup`, **per recipient**, at RCPT when the rules allow and otherwise at enqueue |
| `hook_delivered` (`npLogDelivery.js:9`) | queue worker → **one `/api/delivery` per recipient** |

- **UUID hierarchy** (`internal/uuidx`): `Connection.uuid` = `X`, `Transaction.uuid` = `X.1`, `Delivery.uuid` = `X.1.1`. Hard contract — `tests/smtp/tests/smtp.e2e.test.ts` finds all three with `WHERE uuid LIKE 'X%'`.
- **The `250` reply is deliberate.** `Session.Data` returns `*smtp.SMTPError{Code: 250, ...}`: go-smtp's `dataErrorToStatus` (`conn.go:1257`) passes an SMTPError's code through verbatim, and that is the only way to control the success text. It must contain "queued" and embed the txn id in parens — `tests/smtp/src/smtp.ts:143` scrapes it with `/\(([0-9A-F-]+)(?:\.\d+)?\)/i`.
- **The rule engine** (`internal/ruleset/`) is the reason for the rewrite. `routing.yaml` holds two ordered lists sharing one matcher: `policy` (accept or not) and `routes` (where to send). Predicates are a typed AST — `all`/`any`/`not`/`every`/`always` over `field`/`op`/`value` leaves, with operators `eq ne contains prefix suffix glob regex in in_cidr lt le gt ge exists empty`. Actions are `relay`, `reject`, `tempfail`, `discard`, `quarantine`, `add_header`, `tag`, `accept`; the first five are terminal, `add_header`/`tag` accumulate. Rules sort by `(priority asc, file order)`, first match wins. Non-Turing-complete by design: no loops, no user code, RE2 only.
- **Every field name is checked against a registry** (`schema.go`) carrying its stage and type, so a typo or a type mismatch is a load-time error rather than a rule that silently never fires. `mailgw-go fields` prints it. `header.<name>`, `header_count.<name>` and `tag.<key>` are dynamic prefixes; everything else is enumerated.
- **Stage inference is what fixes RCPT timing.** A rule's stage is the latest stage of any field it mentions, so a rule reading only `rcpt.*` fires at RCPT and its rejection reaches the client on its own `RCPT TO` line. `Route` walks rules in priority order and stops at the first one needing a later stage, reporting "undecided" — so an early decision is provably the one DATA would reach, and can be cached. The `default_action` only applies at DATA, preserving Haraka's `hook_get_mx` timing for "No route found".
- **Two glob dialects, deliberately.** `*` stops at a dot for domain-shaped fields (`*.partner.com` matches `mx.partner.com`, not `partner.com`) and crosses dots elsewhere (`*.exe` matches `report.q3.exe`). A leaf over a list field is **existential**, so `not: {attachment.filename glob "*.exe"}` reads as "no attachment is a .exe"; `every` is the universal form. Implemented in `glob.go` rather than pulling in `gobwas/glob`.
- **`routing.json` still works and transpiles** into the same compiled ruleset (`transpile.go`), so an existing deployment is untouched. Equivalence is asserted, not assumed: `transpile_test.go` runs the legacy matcher and the DSL over the same envelope matrix, and the whole SMTP contract suite runs through the compiled engine. Two legacy bugs are fixed in passing — `Domain()` returns `""` for an address with no `@` (`Route.js:16` returned the whole string), and an unknown relay group is a hard config error rather than a prototype-chain hit (`RoutingTable.js:29` used `name in relays`, so `relay: "toString"` resolved to a Function).
- **Gaps to know about:** `auth.*` and `mail.requiretls` are in the registry but never populated — inbound AUTH is not implemented and REQUIRETLS is not advertised, so `check`, `fields` and startup **warn** when a rule uses one (`unpopulated` in `cmd/mailgw-go/main.go`). Every `attachment.*` field, `msg.has_attachment` and `msg.mime_part_count` are populated as of M8. A recipient refused by a *data-stage* rule gets a DSN instead of the old WARN — but only when the refusal is a 5xx (M7).
- **Per-recipient split** (`session.split`): recipients are grouped by relay group and each group becomes its own envelope `X.1.<k>`, sharing one spooled body.
- **Spool** (`internal/queue`): `tmp/ data/ q/ inflight/ dead/ quarantine/ failed-events/`. Every transition is a `rename(2)` within one filesystem, so a crash leaves a file in its old or new location, never half-written. Queue filenames carry a 12-digit zero-padded due-second, so a lexical sort is due order and nothing needs opening to find the next job. That is also what lets the scheduler sleep until the next envelope is actually due (`Spool.ReadyAndNext` + `Runner.sleepFor`) rather than on a fixed tick — **`outbound.poll_interval` is a ceiling, not a period**, bounding only how long something dropped into `q/` by hand goes unnoticed, so it is cheap to raise. New mail nudges the scheduler immediately and every finished attempt nudges it again. Recovery moves `inflight/` back to `q/`. **A crash mid-SMTP can redeliver** — inherent to any spooling MTA.
- **Bounces are M7** (`internal/dsn` + `internal/queue/bounce.go`). `internal/dsn` builds an RFC 3464 `multipart/report` and knows nothing else — no spool, no routing, no config — so it is pinned by a golden file and shared by both callers; `queue.Bouncer` injects the result and is a standalone type because the SMTP session is its second caller. **Identity nests rather than minting a fresh root**: a bounce for delivery `X.1.2` is `X.1.2.<n>`, which keeps `WHERE uuid LIKE 'X%'` finding the whole tree (a fresh root would leave a `Delivery` row with no `Connection` and no `Transaction` anywhere); `<n>` comes from `Envelope.DSNSeq`, or a delay warning and a later failure would share a uuid and therefore a queue filename. **Four triggers** — permanent rejection, `max_lifetime` expiry, the delay warning (inside `deferEnvelope`), and the SMTP session's post-acceptance refusals — with rejection and expiry collected once per attempt so several failed recipients produce **one** report. **Only a 5xx bounces**: a 4xx, most often `ruleset.DefaultAction()`'s 451, would turn a routing-config gap into permanent rejections. **Routed by the rule engine** against a synthetic null-sender envelope with `msg.is_dsn` set, evaluated at `StageData` (at RCPT one data-stage route rule anywhere would make every bounce undecided); only a relay decision counts, and `dsn.relay_group` is the explicit fallback — the failed envelope's own group would be a guess that usually earns "relay denied". **Never bounce a bounce**: null sender or `IsDSN` is buried in `dead/`, which is **metadata-only** (`Bury` collects the body), so there is deliberately no requeue out of it. The bounce is enqueued **before** `Complete`/`Bury`, so a crash duplicates rather than loses it — `DSNSent` stops a repeat on the *next* attempt, not an exactly-once guarantee.
- **`mailgw-go mailq`** lists all four directories and can `flush`, `rm`, `release` and `hold`. `Spool.Release` **rewrites** rather than renames: `quarantine/` names files `<uuid>.json` and `q/` needs `<due12>.<uuid>.json`, and a bare rename produces a file `parseDue` rejects — invisible to `ReadyAndNext`, still counted by `LenAll`, claimed by nobody. `rm`/`flush`/`hold` **refuse anything in flight**, because deleting the file cancels nothing: the worker finishes and `Reschedule` writes the `q/` copy before removing the inflight one, so `rm` would resurrect what it deleted. `queue.Open` attaches to an existing spool and will **not** `MkdirAll` — a root-owned directory beside the gateway's own is harder to notice than "no such spool".
- **`gcBody` resolves referrers from filenames** (M7), not by parsing every queued envelope. A body is `data/<txn>.eml` and `Envelope.validate` now **enforces** that an envelope may only reference its own transaction's body, so almost every candidate is ruled out unopened. The counter file the plan asked for was rejected: increment/decrement is not crash-atomic, and a lost increment **deletes a live body**. It scans `q/`, `inflight/` **and `quarantine/`** — the omission of the last was a real bug, since `split()` can produce a queued and a quarantined envelope sharing one body. `SweepBodies` runs at bring-up, before the listeners bind, to reclaim what a crash orphaned.
- **`use_mx`** (`internal/deliver/mx.go`) resolves a relay's `exchange` as a domain and expands it into one synthetic relay per MX host — so `tlsConfigFor`'s `ServerName` is the exchanger's own name for free. RFC 5321 §5.1 implicit-MX fallback, RFC 7505 null-MX refusal, and a fixed-TTL cache because Go's resolver does not expose record TTLs. **Not direct-to-MX**: the recipient's domain is never consulted, which would need `split()` to bucket by domain too. **`outbound.reuse_connections`** (`internal/deliver/pool.go`) is **off by default** — it changes what every relay in the field sees (per-connection message caps, connection-keyed rate limits) and nothing observable here shows a need. Pooled connections are RSET-probed on checkout and discarded after any error.
- **Outbound TLS splits by policy (M10).** `tlsConfigFor` gives `TLSOpportunistic` — the default, and what `Relay.TLSPolicy()` returns for any unset or unrecognised value — **`InsecureSkipVerify: true`**, and keeps full verification for `TLSRequired`. RFC 7435 opportunistic security is encryption *without* authentication; verifying under it bought nothing, because the only thing on the other side of the failure was a cleartext redial. Note what actually happened before, which is worse than "silent downgrade": Go completes the handshake **lazily**, so a self-signed certificate was rejected on the *EHLO after STARTTLS*, and the fallback only triggers on a `NewClientStartTLS` error — so an opportunistic attempt against a self-signed MX **failed outright** and the message deferred until it bounced. `res.TLS = true` also moved to *after* that EHLO, since an attempt that never authenticated the peer was being stamped as encrypted on the audit row. **`MinVersion: tls.VersionTLS12`** is now pinned outbound too (inbound and `internal/central` already did); this can break a `tls: required` relay stuck on TLS 1.0. A real downgrade sets `Result.TLSDowngraded` + `TLSDowngradeReason` and is counted and logged in `queue/runner.go` — **not** in `deliver`, which has neither an `obs.Metrics` nor a logger, which is why the signal rides out on `Result` the way `Reused` and `TLS` already do.
- **Shutdown is an ordered teardown** (M9.5, landed with M7): listeners → drain SMTP → cancel the runner → **wait for it** → stop the failed-events replayer (M8; it and the next step both write `failed-events/`) → close the event pipeline, all under one `server.shutdown_timeout` (default 10s, and on the `restartRequired` list because `shutdown` reads `g.live`). `events.Client.Close(ctx)` threads the deadline down to `post`, so in-flight retries abort and the remainder spills to `failed-events/` — **M8 fixed a hole in that**: the shutdown context was read once per event, so a sender already inside `deliver` held `context.Background()` for its whole retry schedule (~37 s on the defaults) while shutdown waited; it is now re-read per attempt, and `Client.done` wakes a backoff that was already sleeping. Both compose files set `stop_grace_period: 30s`; without that the runtime SIGKILLs part-way through and the ordering buys nothing. Measured at 53 ms on an idle gateway, where it used to be a flat 10 s.
- **Events** (`internal/events`): bounded channel → sender pool → timeout + retry, spilling to `queue/failed-events/` on a 4xx (schema mismatch, not worth retrying) or after exhausting retries. `Send` never blocks; a full buffer drops with a counter. Mail flow never waits on the audit trail — but events are now **at-least-once and possibly delayed**, a real change from fire-and-forget. **M8 added the replayer** (`replay.go`): a background pass every `events.replay_interval` (default 5m, `0` disables) plus `mailgw-go events [list|replay|rm]`. Each file is **claimed with a rename** before it is posted, so the gateway's own pass and an operator's CLI run cannot double-post a row; a 2xx deletes it, a **4xx is terminal** and files it under `failed-events/rejected/` (the same reasoning `deliver` already applies — an identical body cannot start passing), and a 5xx or transport error leaves it for next time, aborting the pass after 3 consecutive failures rather than hammering a logservice that is down. It replays to the **current** configured endpoint, not the URL recorded when the event failed, because a managed gateway's logservice URL arrives in a bundle and can change. The spill itself now commits through a tmp+rename with a fixed-width 19-digit nanosecond name and a sequence suffix — `os.WriteFile` could be read half-written, and four sender goroutines could collide in one nanosecond.
- **Attachment scanning is M8** (`internal/attach` + `internal/smtpsrv/attach.go`). Like `internal/dsn`, `internal/attach` knows nothing else — no spool, no config, no ruleset — so it is pinned by `.eml` fixtures and shared by the session and `explain -eml`. It **fixes both `AttachChecker.js` bypasses**: a leaf part counts as an attachment when its disposition is `attachment`, **or it names a file** (which is what `:51` skipped for `Content-Disposition: inline; filename="x.exe"`), or `include_inline` is set and it is not one of the message's own text bodies; and a malformed MIME structure returns the parts found **plus an error**, where `:77` returned "allow". The MD5 is over **decoded** bytes — mailparser hashes decoded content, so every digest already in `BlockMD5s` is a decoded-content digest and hashing the base64 would silently stop matching all of them; `NextRawPart` is used rather than `NextPart` because the latter decodes quoted-printable *and deletes the CTE header*. Bounds (`maxParts`, `maxDepth`) are constants, not config: a MIME bomb is not a tuning knob. **The walk only runs when something will read it** — `attach.enabled` or `Ruleset.NeedsMIME()` — because it is a re-read of the spooled body, which is exactly what `bodyScan` declines to buffer; the shipped default pays nothing. Ordering is **facts → rules → verdict**: the scan runs before the data-stage policy pass so `attachment.*` and `tag.attach_scan` are readable, and `attach.on_block` is applied afterwards and only when no rule reached a terminal action, so an `accept` rule is still the whitelist. `attach.on_block` is `reject` (default, 550) | `tempfail` (Haraka's DENYSOFT) | `quarantine` | `discard`; a scan *failure* under `fail: closed` answers **451**, not 550, because a scanner outage is temporary and not the sender's doing. `mime_part_count` on the queue event is populated for the first time — the field has been on the payload since the Haraka days and this gateway always sent 0. **M10 gave the scan a context**: it is an HTTP call made inside the DATA reply and ran on `context.Background()`, so a hung logservice pinned the session and its goroutine past the whole `server.shutdown_timeout` — the same defect M8 fixed in `events.Client`. `Backend.Ctx` carries the serve context (a `smtp.Session` has none of its own), and `attach.timeout` is now validated as positive when scanning is enabled, since an explicit `0` made both the context deadline and the HTTP client's timeout no-ops. `inactivity_timeout` got the same treatment for the same reason: it feeds `ReadTimeout`/`WriteTimeout` directly, where `0` is an unbounded slowloris, and a bundle is not a file an operator proofreads.
- **Inbound TLS is M8.** `tls.starttls` **defaults to true and is an opt-out**; it is inert without a keypair, so a configuration that never mentions TLS is unchanged. `implicit_tls` on a listener is now actually applied (`cmd/mailgw-go/listeners.go`), with the allowlist `Guard` **outside** `tls.NewListener` so its `550 Access denied` is written inside the TLS session and is readable — the reverse nesting puts cleartext on a socket expecting a handshake. `internal/tlsx` does two things: `EnsureSelfSigned` generates a keypair into the data directory when the configuration names none (a **managed** node only — the same precedent as the Ed25519 identity, since a zero-configuration node has no operator-supplied files, and opportunistic STARTTLS with a self-signed certificate is a substitute for cleartext, not for a real certificate), and `NewReloader` serves the pair through `GetCertificate` with an mtime check, so a certificate **renewed in place** is picked up without a restart — `restartRequired` compares cert *paths*, never contents. **A private key never travels in a bundle**: the console stores versions forever and serves them to every gateway on the profile. An operator drops a real pair in `/opt/mailgw-go/data/tls/` and names `/var/lib/mailgw-go/tls/…` in a server profile; no compose change and no bundle format bump. go-smtp calls `Backend.NewSession` a second time after a STARTTLS upgrade, so policy is re-evaluated on the encrypted session — `TestTLS_PolicyIsReevaluatedOnceAfterTheUpgrade` pins that it happens and that the refusal is counted once.
- **Allowlist** (`internal/config/allowlist.go`): now CIDR- and IPv6-aware, still **fail-closed** — a missing or malformed `ngmfilter.json` denies everything (`npFilter.js:52-57`), and the zero value denies, so ignoring a load error cannot open the relay. Starting with an empty allowlist is refused unless `allow_all: true`. `ParsePrefixes` is exported so `listen[].proxy_trusted` reuses the same parser, masking and `::ffff:` normalisation.
- **Message limits are enforced and permanent (M10).** `max.bytes`, `max.line_length`, `max.received_headers` and `max.header_lines` all refuse **5xx** now; every one of them used to collapse into a single `451 4.3.0 cannot queue message`, so a message whose size or format could never become acceptable was retried for its whole `max_lifetime` and its sender got a delay-expiry bounce that said nothing about why. `received_headers` and `header_lines` were **dead config** until M10 — declared, defaulted, and read by nothing — which meant the config key that looks like a mail-loop guard was not one. Size → `552 5.3.4`, header lines → `552 5.3.4` (via a sticky sentinel on `bodyScan`, since `captureHeader` has nowhere to return an error and `Spool.WriteBody` already wraps with `%w`), line length → `500 5.5.2`, hop limit → `554 5.4.6` + `msg_loop_rejected`. All go through `session.refuse()`, which is documented as the only place `msg_rejected`/`msg_tempfailed` move. **`smtp.ErrTooLongLine` does reach the gateway during DATA** — go-smtp answers it itself only for *command* lines (`server.go:192`) — which is the opposite of what M10's plan assumed.
- **PROXY protocol is `internal/proxyproto` (M10)** — v1 text and v2 binary, hand-rolled and stdlib-only, on the same reasoning as `internal/obs` over `client_golang`. It exists because the IP allowlist is the only inbound gate until M13, so behind an L4 balancer every connection arrives from one address and allowlisting it opens the relay to everything behind it. Wired **innermost**: `tcp → proxyproto → Meter → tls.NewListener → Guard → Limit → srv.Serve` (the cap's two links are M11 and M16), because the header precedes the TLS handshake and `tls.Conn.RemoteAddr` delegates downward. The header **cannot** be parsed lazily on first `Read`, nor inside `RemoteAddr()` (what `pires/go-proxyproto` does): `Guard` reads `RemoteAddr()` synchronously in its own accept loop, so either would decide allow/deny before the header was known, or block that same goroutine. Instead the **trust check runs before the first byte** — an untrusted peer costs one `accept`+`close`, no parser slot and no deadline — and a bounded worker pool resolves headers off the accept path. Fail-closed on a missing, malformed or untrusted header, counted as `proxy_dropped`. Per-listener `proxy_protocol` + `proxy_trusted` (required non-empty; an empty list would mean "drop everything", and `proxy_trusted` without `proxy_protocol` is an error rather than a silently ineffective key). `v2 LOCAL` and `v1 UNKNOWN` mean "no proxied client", so a balancer's health check is judged on its own address. The conn wrapper must return a **`*net.TCPAddr`** — `session.go:116` type-asserts it with no fallback — and buffers bytes over-read past the header, or a ClientHello arriving in the same segment would be lost.
- **Testing**: `internal/smtpsrv/contract_test.go` ports every assertion from `tests/smtp/tests/smtp.test.ts` so the SMTP contract runs under `go test` without Docker. The Bun suite runs **unmodified** against the binary via `SMTP_PORT=2525 bun test tests/smtp`. `internal/deliver` tests use real go-smtp instances as fake relays.
- **Central management is done (M3–M6), and the shipped node is zero-configuration.** The image runs with **no `CMD` at all**: no environment variables, no CLI arguments, no config files on the host. It boots empty, generates an Ed25519 identity, serves an unauthenticated local wizard, and takes everything else from Central Management into a local SQLite cache. `internal/store` is pure-Go SQLite (`modernc.org/sqlite` — the image is `distroless/static` with `CGO_ENABLED=0`, so cgo drivers are out; ~6 MiB of binary), `internal/central` is the Ed25519 signing client, `internal/adminui` is the wizard (stdlib only).
  - **`-config` on the command line is what selects file mode**, byte-identical to before — it is what keeps `check`, `explain`, `testdata/config`, CI and the Bun SMTP suite working, and the dev compose pins it for that reason. Absent, the gateway is managed: it **does not serve SMTP until a deployed bundle applies** (a gateway with no allowlist denies every peer anyway, and a listener that can only reject looks healthy to a load balancer).
  - **`serveFile` and `serveManaged` converge on one `*gateway`** (`cmd/mailgw-go/gateway.go`), brought up from a `*loaded` exactly once. The **first** apply builds the spool, events client, runner and SMTP server and starts listening; **every later** apply swaps only the allowlist and the compiled rules, via the same `atomic.Pointer`s SIGHUP always used. `restartRequired(live, next)` names what changed that a restart is needed for (`relays, listen, tls, hostname, greeting, local_domains, max, smtputf8, inactivity_timeout, log, outbound, dsn, attach, events, logging`) — a list, not a bool, because "restart required" with no reason is an alarm nobody can act on. `hostname` and `logging` are on it because `smtpsrv.Backend.Cfg` is captured at bring-up and read live at session time.
  - **Boot follows the console's recorded intent** (`desired_version_id`, a store setting), not a timestamp. `applied_at`/`fetched_at` have one-second resolution and a rollback lands in the same second as the deploy it undoes, so either ordering would tie-break on `version_id` — the very bundle the operator just rejected. `applied_seq` (store migration 2) makes "most recently applied" answerable for the same reason. A **partial** apply is still marked applied, or the restart the console asked for would boot the old bundle.
  - **Rollback needs no gateway-side feature**: the console repoints at an older version whose bytes are still cached, so nothing is fetched and what runs afterwards is byte-identical. Re-using cached bytes refreshes `fetched_at` so the rollback survives a restart.
  - `bundle_sha256` is treated as an **opaque change token, never recomputed** — Fastify re-serialises the bundle on the way out, so the wire bytes are not the bytes that were hashed.
  - **`GET /agent/ws`** (`internal/central/ws.go`, `github.com/coder/websocket`) makes a deploy land in milliseconds instead of on the 15s poll. The upgrade carries the same Ed25519 signature, so there is no new auth. Frames carry **no state** — the gateway is told "go and look" and asks `/agent/status` — so a duplicated or delayed notification is harmless and a socket that never connects costs only latency. The dialer must use an **HTTP/1.1** transport: `ws` speaks the HTTP/1.1 upgrade, not RFC 8441 over h2, which is why the console's `allowHTTP1: true` matters.
  - **`check` and `explain` read the cache too** (`-data`), and `config show` prints the running bundle with `auth_pass` and `api_key` redacted — the managed-mode equivalent of `cat routing.yaml`.
  - **The admin UI is always listening**, because the wizard is the only provisioning path, and **M12 locked it behind a claim code**. Because the console is HTTPS-only with a self-signed pair, the wizard also carries a TLS-trust checkbox and an optional CA-bundle path. `deploy/gateway/05-firewall.sh` is **still required, not optional**: what an authenticated caller can do is re-point the gateway at a hostile Central Manager and be handed its relay credentials, and on an edge node that is a root process with no port mapping to narrow — authentication made the firewall one control of two, not a spare.

- **Admin UI authentication is M12** (`internal/adminui/auth.go`, `internal/store/admin.go`). A managed gateway mints a **claim code** on first boot — 100 bits in Crockford base32 (no `I L O U`, normalised on input, so it can be dictated) — logs it at WARN while unclaimed, and shows one page to anyone without a session: version, fingerprint and a field for the code. **The code is deliberately not consumed**, contradicting M12's own plan: a single-use code plus a cookie leaves the node reachable by exactly one browser for ever, and what must not reopen is the *unauthenticated* window, which closes the moment a code exists. `admin_claimed_at` only records first use, which is what stops a live credential being re-logged on every boot. It is stored in **plaintext** — the same 0600 database holds the Ed25519 seed, so hashing protects nothing, and plaintext is what lets `mailgw-go claim status` answer "I lost it" **without rotating** and signing every other operator out. `claim reset` mints a new code and revokes every session in one transaction. **Sessions live in SQLite** (store migration 3, `admin_sessions`, 12h absolute, swept on creation only so a GET never writes): a restart is most likely *during* provisioning, the per-session CSRF token has to survive with its session, and `claim reset` needs somewhere to revoke all of them. Nothing is cached on `*Server` — a cached session would outlive a `claim reset` run from a second process. **Middleware wraps each route rather than the mux**, so `Handler()` reads as the policy and a forgotten wrapper is a visible omission; `/` is session-*aware* rather than gated, because a 403 there leaves an operator nowhere to sign in and would hide the fingerprint that exists to be pre-approved. The **claim throttle is in memory** (5 tokens, 1/s, 429, never sleeps): a counter in the store would make `POST /claim` an unauthenticated write to the gateway's own database — a DoS primitive — against a brute force 100 bits already prevents, and sleeping inside the 30s `ReadTimeout` would let an attacker park goroutines until real claims queued behind them. Cookie: `HttpOnly`, `SameSite=Lax` (Strict adds only top-level-GET protection over the CSRF token, and costs a baffling cross-origin-link report), **`Secure` iff `r.TLS != nil`** (unconditional `Secure` over this plain-HTTP listener is simply never stored, so the UI would sign nobody in), no `Max-Age`. **`/metrics` and `/readyz` take a bearer token instead** — a scraper has no browser — from `admin.metrics_token`: `admin.json` in file mode, the bundle's `admin` key under central management (console env `GATEWAY_METRICS_TOKEN`, omitted when empty so no digest churns), redacted by `RedactBundle` beside `logging.api_key`. Empty means **open**, `/healthz` is always open, and the token is read from `gateway.adminToken atomic.Pointer[string]` set on both successful apply paths — a **third category** beside "hot-swapped" and "needs a restart", so it is deliberately absent from `restartRequired` and a failed apply keeps the last-good value. **File mode is untouched** (`Store == nil` passes the middleware through). The listener **stays plain HTTP**, decided rather than implied: a self-signed pair authenticates nothing and teaches an operator to click through a warning on the page where they type a secret; `-admin-tls` with real paths, never in a bundle, is the tracked follow-up.
- **Inbound SMTP AUTH is M13** (`internal/smtpsrv/auth.go`). The session implements `smtp.AuthSession`, so go-smtp advertises `AUTH PLAIN LOGIN` — but only when a credential set is configured *and* `authAllowed()` is true, which means an encrypted session or `tls.allow_insecure_auth`. Three independent switches, all off in a configuration that says nothing. `go-sasl` supplies `NewPlainServer` but **no LOGIN server** (only the client), so that half is ~40 lines here; the milestone still adds no SASL dependency, though it does add **`golang.org/x/crypto/bcrypt`** — the module's seventh direct dep — because verifying a password is not SASL's job and one hashing story with the console's `bcryptjs` beat inventing a stdlib PBKDF2 encoding for both sides to agree on. A bad credential answers **`535 5.7.8`**, not go-smtp's flat `454`, which would tell a client to retry the same wrong password; the `*smtp.SMTPError` passthrough is the same mechanism `Session.Data`'s deliberate `250` uses. An unknown username is still compared, against a fixed dummy hash, so AUTH is not a username oracle, and concurrent bcrypt comparisons are bounded to `GOMAXPROCS` so a credential-stuffing run cannot starve the delivery runner of CPU — a floor under the damage, not a limiter, which is M15. **The identity lives on the session, not on `env.Helo`**: `Mail` rebuilds the helo env from `heloEnv()` on every transaction, so writing the `HeloEnv` directly is silently discarded at MAIL. `auth.user`, `auth.mechanism` and the new `auth.authenticated` are registered at **`StageMail`**, not `StageHelo` as the plan assumed — connect- and helo-stage policy is evaluated inside `Backend.NewSession`, and go-smtp will not process `AUTH` until EHLO has been answered, so a helo-stage rule would be read before the client could possibly have authenticated. Removing the first two from `unpopulated` is the milestone's completion signal. Credentials are a **third category** beside "hot-swapped" and "needs a restart" — `gateway.authUsers atomic.Pointer[config.Auth]`, read per AUTH command so a revocation lands on the next attempt, deliberately absent from `restartRequired` — while `tls.allow_insecure_auth` sits in the `tls:` block precisely because it *is* read once at bring-up and the `tls` entry already covers it. `gateway.warn` says so when credentials are configured but AUTH can never be advertised. Console side: `CredentialSets`/`SmtpCredentials` (migration `026`) with every `/config/credentials/*` route **admin-only including the index**, because a list of submission usernames is a list of what to guess passwords against.
- **Inbound DSN is M13 too** (`internal/dsn`, `internal/queue`). `EnableDSN` follows `dsn.enabled`, so the capability is advertised exactly when this gateway generates notifications. `ORCPT` rides on `queue.Recipient` to `Original-Recipient`, **re-encoded as xtext** — go-smtp decodes on the way in and exports no encoder, and `+` is an xtext special, so `user+tag@example.com` emitted raw decodes into something else. `NOTIFY` decides who is told: absent means `FAILURE` per RFC 3461 §4.1, `NEVER` silences a recipient without silencing the report for the others (which is what makes it different from `Suppress`), and **delay warnings follow Postfix's reading** — suppressed only when the sender *supplied* a NOTIFY that omits `DELAY`, because the strict reading would switch off `delay_warning_after` for essentially all mail. `RET` overrides `dsn.return` per message but never escapes `max_return_bytes`. `NOTIFY=SUCCESS` earns a `dsn.KindRelayed` report — "relayed", never "delivered", since a relay accepting a recipient says nothing about what happened next — because this gateway does not pass DSN parameters to the next hop and §5.2.7 makes it the boundary that answers for them. Every new envelope field is an `omitempty` addition at `EnvelopeVersion` 1, as `Envelope.DSNSeq`'s comment requires: bumping the version would make `validate` reject every envelope already on disk and `Claim` would park the whole live queue in `dead/`. **Two pre-existing defects came out with it.** `Original-Envelope-Id` was carrying this gateway's own uuid where RFC 3464 §2.2.1 defines the sender's `ENVID` — a receiving system matching that field got a confident non-match against something that looked like one; the uuid moved to `X-NGM-Original-Envelope` and the golden file was regenerated. And a notification's body was named for the envelope it *reports on*, so two notifications about one envelope **overwrote each other's bytes** — a delay warning at four hours and a failure at four days already could, and a mixed-outcome message with `NOTIFY=SUCCESS` does it every time. Bodies are now named for the notification itself, which needed the ownership rule relaxed to "its own name or an ancestor's" in `Envelope.validate` **and** in `Spool.bodyReferenced`, which uses the same rule as a shortcut — a shared `bodyOwnedBy` helper, because if those two disagreed the disagreement would delete a live body.
- **Message authentication is M14** (`internal/msgauth`). SPF at MAIL, DKIM and DMARC at DATA, an `Authentication-Results` header recording all three, and DKIM signing on the way out. Like `internal/dsn` and `internal/attach` the package knows nothing about the spool, the session, the config or the rule engine, so it is fixture-pinned and shared by the session and `explain`. **Every result is a rule field** — `spf.result`/`spf.domain` (StageMail), `dkim.result`/`dkim.domains`/`dmarc.result`/`dmarc.policy` (StageData) — under their own prefixes rather than `auth.*`, which since M13 means "this *client* authenticated". **Nothing is refused that was not refused before**: there is no `on_dmarc_fail` key, and what to do about a failure is a rule an operator writes, per the plan's own "deliberately not done". Each check ships **off** and is turned on by its `msgauth:` key *or*, on its own, by a rule reading its fields (`Ruleset.NeedsSPF`/`NeedsDKIM`/`NeedsDMARC`, computed once at compile time from `FieldsUsed()` — the `NeedsMIME` precedent), so a configuration that never mentions it pays nothing. **Two dependencies, taking the module to nine**: `emersion/go-msgauth` for DKIM/DMARC/`authres` (same author as `go-smtp`; its three packages import only stdlib plus `x/crypto/ed25519`, so no new indirect build) and `blitiri.com.ar/go/spf`, which the plan expected to hand-roll — its `DNSResolver` is `*net.Resolver`-shaped, so one map-backed stub serves SPF, DKIM and DMARC and no test touches the network. **The plan was wrong in four places**, all recorded in its "What was built differently": the headers cannot go in `receivedHeader()` (written *before* DATA is read, so the DKIM result does not exist yet — they ride on `txnHeaders`, which brings `sanitizeHeaderValue` for free and lands them above our own `Received:` via `PrependBlock`, the ordering RFC 7601 wants); signing cannot go in `internal/deliver` (`Message.Body` is a one-shot reader and a signature precedes bytes the signer consumed — `queue.Signer` opens the spool twice instead, and deliberately does *not* use `dkim.Sign`, which buffers the whole message in RAM); stripping *every* inbound `Authentication-Results` overshoots RFC 7601 §5, which asks only for the ones forging our own authserv-id — so a trusted upstream's results survive and the filter is byte-for-byte identity otherwise; and the fields are namespaced. **Two invariants the plan did not anticipate.** A check that did not run reads as **absent**, not `none` — `none` asserts that a check ran and found no policy, so `spf.result eq "none"` cannot match a gateway that never looked, and `FormatAuthResults` omits a method rather than claiming it. And `DKIMResult.Domains` carries only signatures that **verified**: a `d=` on a broken signature is a claim anybody can attach, and crediting it would let a forger pass DMARC by bolting an invalid signature naming the victim onto a message. **The signing key is chosen by the `From` header domain**, so `d=` aligns and DMARC credits it downstream; keying off the envelope sender is valid, costs the same and buys nothing whenever the two differ — which is every forwarded message and every bounce this gateway generates. Signing failures are **soft**: no key for a domain is a Debug line, a key that will not load is a Warn and the message goes out unsigned, because refusing to relay over a file permission would turn a configuration slip into a mail outage. **A private key never travels in a bundle** — only the selector, the domain and a path — and unlike `tlsx.EnsureSelfSigned` nothing is generated, because a self-generated key whose public half is not in DNS produces signatures that *fail*. There is **no public suffix list**, so DMARC's organizational-domain fallback and relaxed alignment are approximated (one label up; "equal or a subdomain of"), both erring towards `none`/`fail` rather than a false pass.
- **Rate limiting is M15** (`internal/ratelimit`). The other half of the pair M11 started: `max.connections` bounds how many connections exist *at once*, this bounds how *often* anything happens — a peer opening one connection at a time and pushing a million messages through it never trips a concurrency cap. Five dimensions in a `ratelimit:` block — `connect_per_ip` (421, in the listener chain), `messages_per_sender` and `messages_per_user` (450, at MAIL), `rcpts_per_domain` (450, at RCPT, **per recipient** so the rest of the transaction continues), `auth_failures_per_ip` (454, before the bcrypt compare). **Every limit ships off and every refusal is a 4xx** — the milestone is designed against one failure mode, a limit set too low turning into permanently rejected mail, which is M7's "only a 5xx bounces" seen from the other end. **Named `ratelimit:` and not `limits:` as its plan said**, because `max:` already unmarshals into `config.Limits` and `max.connections` beside `limits.connect_per_ip` is exactly the pair an operator sets the wrong one of. **Token buckets, not the sliding windows the plan named**: a window keeps the timestamps still inside it, so its memory per key grows with the configured rate and "bound the map" means bounding a quantity nobody can predict — and, more importantly, a bucket refilled to capacity is *byte-for-byte what the limiter would create for that key*, which makes eviction provable rather than heuristic (`evictLocked` is that sentence in code). **The placement rule inverts M11's, and the resource is why.** The connection cap sits *outside* `Guard` because it bounds a process-wide semaphore and an unlisted peer holding a slot would make the cap the attack; this limiter sits *inside* `Guard` because it bounds a **map**, and outside it that map is keyed by the internet rather than by the allowlist — the limiter would become the memory-exhaustion vector it was added to prevent. It also sits before `Limit`, so a peer over its rate never spends a semaphore slot: `tcp → proxyproto → Meter → tls → Guard → Throttle → Limit → srv.Serve`. **A third category beside `authUsers` and `adminToken`** — read live, deliberately absent from `restartRequired`, because a limit an operator cannot adjust without restarting a mail server during an incident is a limit they will not use — but note the limiter object is created **once, at gateway construction**, and only its *rules* are swapped: replacing it per apply would hand every peer a fresh allowance whenever an unrelated change was deployed, so an attacker under pressure would be released by a routine deploy. Consequently **raising a limit gives faster relief, not instant relief** (2/hour → 50/hour turns a 30-minute wait into a 72-second one). Three invariants the plan did not anticipate: **only failures spend the failed-AUTH budget** (hence `Blocked`/`Spend` beside `Allow` — the key says `auth_failures_per_ip`, and spending on every attempt would throttle exactly the clients behaving correctly); **a full map admits rather than refuses**, because refusing what cannot be tracked turns a memory ceiling into a mail outage *and* lets an attacker deny service to everyone by filling the map; and **the null sender is never limited**, since every bounce in the world shares it and one bucket for all of them would refuse precisely the notifications this gateway most needs to deliver. The counters are in memory and **per gateway** — ten nodes at 100/min admit 1000/min — which is the right trade against a network round trip in the accept path. `454` rather than `421` for AUTH is a compromise recorded in the plan: go-smtp's `handleAuth` never closes the connection, so 421 would announce a disconnection that does not happen.
- **Observability is `internal/obs` (M6)** — a hand-rolled atomic counter registry, ~300 lines, **no `prometheus/client_golang`** (it would be the module's largest dependency and the text format for a counter is three lines). One table drives both the `Snapshot()` keys (a **console** contract, travelling in the heartbeat) and the `mailgw_*` Prometheus names (a **dashboard** contract); a reflection test asserts every `atomic.Int64` field appears in it exactly once, and a golden test pins the snapshot keys (**46 as of M15**, which added `rate_conn`, `rate_sender`, `rate_user`, `rate_rcpt_domain` and `rate_auth` — one per limited dimension, because one counter for all five would not say which limit to raise, and in three different units: connection, message, recipient; note `rate_auth` is **not** a subset of `auth_failed`, since a refusal there happens before any password is compared, and the two together are what credential stuffing looks like; M14 took it to 41 with `spf_checked`, `spf_failed`, `dkim_verified`, `dkim_signed` and `dkim_sign_failed` — the first three per inbound *message*, the last two per outbound *envelope-attempt*, and `spf_failed` a subset of `spf_checked`; M13 took it to 36 with `auth_ok`, `auth_failed` and `dsn_notify_suppressed`, M11 to 33 with `conn_throttled` and `events_dropped`, and M10 to 31 with `deliver_tls_downgraded`, `msg_loop_rejected` and `proxy_dropped`). DMARC deliberately gets no counter: it is a function of the two beside it, and a counter should name a thing that moves. **Three units that must not be mixed** — *message* (one transaction), *recipient* (one RCPT), *envelope* (one spooled file) — stated in every HELP string, because `msg_accepted` is a **superset** of `msg_discarded`/`msg_quarantined` (a message every rule dropped is still answered 250) and `deliver_connfail` is **per relay** while `deliver_deferred` is **per envelope-attempt**. `DeliverDeferred` lives in `Runner.deferEnvelope`, not `record` — `record` `continue`s on deferred outcomes and never runs when every relay failed to connect; `deferEnvelope`'s three call sites each end the attempt, giving exactly one per attempt. Gauges are read at scrape time and **omitted rather than zeroed** when unknown (`Gauges.QueueOK`): a managed gateway has no spool before its first apply, and a fabricated `0` reads as "drained" when it means "unreadable". `Spool.LenAll()` returns a `Counts` struct covering `q/ inflight/ quarantine/ dead/` plus, since M8, `failed-events/` and, since M11, `failed-events/rejected/` — those last two **tolerate the directory being absent**, unlike the four before them, because a spool from before they existed is still a valid spool and "no such directory" means zero parked events, not a broken gateway. `Len()` remains a two-value delegate for its six existing callers.
- **Resource bounds are M11.** Six ceilings that did not exist plus one counter, all inbound or in a long-lived cache, where nothing bounded growth. **`max.connections`** (default 1024, validated positive on the `inactivity_timeout` precedent — an explicit `0` from a console textarea would mean "no cap", which is the state the key exists to end) is a **process-wide** semaphore in `internal/smtpsrv/limit.go`, one channel shared by every listener because what it bounds is this process's file descriptors. It answers `421 4.7.0` and closes rather than blocking the way `netutil.LimitListener` does, and its **admission** sits **outside `Guard`** — because inside it, a peer the allowlist is about to refuse would hold a slot until `Guard.deny` closed it, so a flood from unlisted addresses would fill the semaphore and throttle real senders: **the cap would become the attack**. Consequently `conn_throttled` is a **subset** of `conn_accepted`. **M16 split it in two**, because M11 also *wrapped* the accepted connection to release the slot on `Close`, and go-smtp finds TLS by a bare `c.conn.(*tls.Conn)` assertion (`conn.go:189`, `server.go:164`) with no unwrap interface: on an `implicit_tls` listener that wrapper made the session report no TLS to `conn.tls`, the `Received:` header (`ESMTP`, not `ESMTPS`) and the audit row, be offered STARTTLS inside TLS, and — the leak — skip `server.go:164`'s pre-handshake read deadline, the only one go-smtp arms before `greet`, so a peer that connected and stayed silent parked its session goroutine and its slot for ever. The chain is now `tcp → proxyproto → Meter → tls.NewListener → Guard → Limit → srv.Serve`: `Meter` (below TLS) returns an *unarmed* `slotConn` and owns the release; `Limit` (outside `Guard`) decides admission, arms the slot it finds beneath the connection via `NetConn()`, and hands the connection on **unwrapped**. `slotConn.Close` still needs a `sync.Once` because go-smtp closes a session's conn and `Server.Close` closes it again. Both refusals — the cap's `421` and `Guard`'s `550` — are now written on a bounded goroutine pool behind a full `SetDeadline`, since writing inline on a TLS listener runs the handshake in the accept loop and its ClientHello read was bounded by nothing. **`central.do` bounds the response body once** (`maxResponseBody`, 8 MiB) rather than only the decoder: the deferred `io.Copy(io.Discard, …)` that exists for connection reuse runs on the failure path too, so capping the decoder alone would fix memory and not bytes-read. It reads-then-`Unmarshal`s rather than streaming, because a decoder cannot distinguish "too big" from "truncated"; `ErrResponseTooLarge` is deliberately **not** an `HTTPError`, so `IsUnreachable` is true and the poll loop keeps the last-good configuration. **`failed-events/rejected/`** gained `mailgw_failed_events_rejected` and an `events.rejected_retention` sweep (default 30 days) that rides the replay pass — so `replay_interval: 0` disables it, and the gateway WARNs at boot when it would. The **MX cache** sweeps expired entries on write *and* carries a hard `maxCacheEntries` constant, because a sweep reclaims nothing from a workload wider than the cache within one TTL; past it the map is dropped whole, since being wrong costs one DNS lookup. **`events_dropped`** exposes the one audit loss that is unrecoverable — a spilled event is on disk and replayable, a dropped one was never written anywhere.
- **M16 is the re-audit of M11**, run over its own code before it was committed, on the premise that a green suite proves nothing — and every M11 test builds its subject directly while three of its items only take effect through `cmd/mailgw-go`'s wiring, which had **no test at all**. Besides the cap (above), it fixed: `connGuard.release` ignoring `context.AfterFunc`'s stop result and never clearing `g.conn`, so a cancellation arriving in that window closed a pooled connection **another delivery had already taken** (it now clears the conn under the same mutex `closeConn` blocks on); `Pool.Put` holding `p.mu` across a `QUIT` that waits for a reply, serialising every other `Get`/`Put`/`Reap` behind an unresponsive relay; the pool's RSET checkout probe running **before** the guard was armed and before `applyTimeouts`, so it could not be cancelled at all — `Pool.Get` now takes a `prepare` callback that runs on each candidate first; `Pool.Close` closing serially outside the shutdown deadline; `MaxMessages` never firing on all-recipients-rejected envelopes; MX domains not being lower-cased and the equal-preference shuffle being cached with the answer (so RFC 5321 §5.1 spreading happened once a TTL, not once a message); `outbound.connection_idle_timeout: 0` silently disabling all three eviction paths; the `LastErr` switch having no arm for "the relay answered and deferred everybody", so `mailq -json` reported the *previous* attempt's connection failure for a greylisted message (blank on a first attempt); `reject()` filing rejected audit events with `os.Rename`, which **preserves mtime**, so the retention sweep measured age-since-*spill* and deleted an old event on the same pass that filed it; a replay claim left by a killed process being invisible for ever (`Replayer.Reclaim`, 15-minute grace, claim time in the filename because the mtime is already load-bearing for `handleUnparseable`); and `events.Client.Send` after `Close` returning silently — uncounted — while `close(c.ch)` could make a racing send **panic the process** from the audit path, which is why nothing closes that channel any more. `events.replay_interval`/`rejected_retention` now reject negatives, and the HELP strings that claimed `events_replay_failed` is "4xx" name the other two causes. No new counters: the golden snapshot list stays at **33**.
- **Two delivery traps M11 closed.** The connection guard **did not cover pooled connections**: `guard.use` was only ever called inside `connect`, so with `outbound.reuse_connections` on, context cancellation could not interrupt an in-flight DATA on a reused connection and it ran to `SubmissionTimeout` (10 minutes by default), well past `server.shutdown_timeout`. `pooled.conn` and a `closer` interface were declared and never assigned — the half-built other end of exactly this; they are now a real `net.Conn` carried through `Pool.Put`/`Get`. **`Deliver`'s defers run LIFO**, so `Pool.Put` runs *before* `defer guard.release()` — once the guard reaches a pooled conn that ordering is load-bearing, and `guard.release()` is now the first statement inside the pool-disposition defer. Two neighbours came out with it: `applyTimeouts` and `recordPeer` never ran on the reused path, so a pooled client kept its first dial's budgets and the audit row carried no peer IP. `Pool.Reap` also enforces `connection_idle_timeout` on a schedule instead of only when a connection is next borrowed, and drops map keys whose slice empties (`poolKey` is built from `relay.Addr()`, so with `use_mx` the key set follows DNS). Separately, **an MX resolution failure lost its error**: with every group member `use_mx` and DNS down, `targets` returned nothing, the relay loop never ran, and the envelope deferred with `LastErr` unchanged — or, on a first attempt, **blank**, since `deferEnvelope` only overwrites a non-empty reason. That field is the only evidence in this case (no relay was contacted, so no recipient carries a `LastMsg`), and both `mailq -json` and the expiry DSN read it.
- **`GET /metrics`, `GET /readyz` and `GET /healthz`** all sit on the M4 admin listener. `/healthz` is liveness-only; **`/readyz` performs no I/O at all** — it reads the snapshot the last successful poll left behind, because readiness that depended on reaching the console would turn one console outage into a fleet-wide 503 and a management-plane failure into a mail failure. Ready = provisioned + approved + a configuration applied + serving; in file mode (`Store == nil`) just serving. A failed poll, a failed deploy of a *new* version and a pending restart are deliberately **not** conditions, and the fixed reason strings never echo `State.LastError` (untrusted operator-visible text). **The heartbeat is one line in `agent.report`** — `central.Report.Metrics` and the console's schema both already existed — folded into the existing 15s poll rather than a second ticker, so it is bursty by design (the loop also wakes on the WebSocket) and there is nothing there to rate-limit.
- **Every audit row carries a `gateway` label** (logservice migration `023`), resolved **once at bring-up** — the `gateway_uid` when managed, `server.hostname` in file mode — never per event, and truncated to 64 characters **with a warning**, since silent truncation would make two gateways indistinguishable. Delivery rows also carry `route_rule`, the rule that chose that recipient's relay group: **per recipient**, carried on `queue.Recipient.RouteRule` and set in `session.split` from `decision.Rule`, because one envelope groups by relay group and can hold recipients routed there by different rules — which is why there is no `route_rule` on `Transaction`.
- **Two defects M6 fixed in passing.** A **`stage: mail` `discard`/`quarantine` was silently ignored and the message relayed**: `ruleset/eval.go` only compile-rejects those actions *before* MAIL, so the rule compiled and `applyTerminal` fell through to `return nil`. It now records the drop on the session and `Data` honours it (`TestMailStageDiscardIsHonoured` fails without the fix). And `agent_pull_test.go` read the report body with a single unchecked `Read`, which the metrics object pushed past the size where that happened to work.

> **Companion change in `logservice/`:** the delivery schema was incompatible with an outbound queue, not merely strict — `sender` rejected the null sender every bounce uses, `host` rejected `localhost`/`dev-mailhog`/IP literals, and `ip` was IPv4-only. `src/validation/delivery.ts` now accepts these; `migrations/015` widens `Delivery.response`/`rcpt_list` to TEXT and adds the first indexes on `uuid` columns. `rcpt_list`/`rcpt_accepted` stay **single-valued** — that is the contract mailgw-go now honours.

### DEV mode

Setting `MODE=DEV` (`pnpm legacy:dev`) enables extra JSON logging to `log/ngmroute.log` inside `npRoute.js`. Log files are written to `log/` relative to the Haraka working directory (`legacy/mailgw/` locally or `/opt/mailgw` in Docker).
