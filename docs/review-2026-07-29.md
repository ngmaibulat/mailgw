## 1. logservice

### 1.1 SQL injection via `searchLogic` — **Critical** — ✅ FIXED

`src/query/builder.ts:96` (pre-fix) interpolated the join operator straight into the
`WHERE` clause:

```ts
sql: conditions.length > 0 ? conditions.join(` ${logic} `) : "",
```

`logic` was *typed* `SearchLogic` (`"AND" | "OR"`) but never checked at runtime — types
are erased, and the value came from the caller-supplied `?q=` JSON via
`parseSearchQuery`, which was a bare `JSON.parse(raw) as SearchQuery` cast. Every caller
(`src/query/search.ts:70, 79, 88, 101`) passed it through to `db.unsafe(sql, values)`.

Reachable on all four search endpoints: `/api/delivery`, `/api/connection`,
`/api/transaction`, `/api/hashlookup`. With two valid search params the payload
preserves placeholder arity, so it executed cleanly:

```
GET /api/delivery?q={"searchLogic":"OR 1=1 OR","search":[
  {"field":"sender","operator":"is","value":"nosuchsender"},
  {"field":"host","operator":"is","value":"nosuchhost"}]}
```

→ ``WHERE `sender` = ? OR 1=1 OR `host` = ?``.

**Confirmed exploitable against a running instance:** pre-fix this returned all rows in
the table despite both filters matching nothing; post-fix it returns `total: 0`. Blind
exfiltration across tables (`AND \`id\` IN (SELECT id FROM Users WHERE hash LIKE 'a%')
AND`) and time-based (`AND (SELECT SLEEP(5)) AND`) variants worked the same way.
Stacked statements are blocked by the MySQL prepared protocol, so this was
read/blind-read, not DDL — still full data disclosure.

Exposure was **unauthenticated on the default stack**: `docker-compose.yaml:51` sets
`API_KEY: ${API_KEY:-}`, which makes `withAuth` a no-op (§1.2), while
`docker-compose.yaml:47` publishes the service on `0.0.0.0:3000`. On the `deploy/core`
stack, where `API_KEY` is required, it still escalated a log-read credential into a read
of any table the DB user can see — including `Users.hash` and the plaintext
`Relays.auth_pass`.

The webui proxy was *not* a viable path: it already validates `searchLogic` as an enum
(`webui-fastify/src/validation/search.ts:46`). The published port was.

**Fix applied:**

1. `buildWhere` now re-normalises the operator to a literal before interpolating —
   `String(logic).toUpperCase() === "OR" ? "OR" : "AND"` — so anything unexpected
   degrades to the safer, more restrictive `AND` and can never reach the SQL string.
   This mirrors the direction handling `buildOrderBy` already used, and holds for every
   caller including any that bypass `parseSearchQuery`.
2. `parseSearchQuery` no longer casts: non-object payloads (`null`, strings, arrays)
   return `{}`, and `searchLogic` is narrowed to the union it claims to be. This is a
   second layer, not the one that makes injection impossible. It also removed the
   `?q=null` → 500 noted in §1.5.
3. `tests/builder.test.ts` gained regression coverage for hostile, mixed-case, junk and
   missing `logic` values, plus subquery/time-based payloads, and for
   `parseSearchQuery`'s handling of non-object JSON. The suite went from 30 to 81
   assertions.

Note on why this survived: the existing tests covered every operator, but **every call
site hardcoded `"AND"`/`"OR"`**, so the one untrusted input was never exercised.

The rest of the builder was and remains safe: values are bound `?` placeholders, field
names are gated on `allowedFields` before backtick interpolation (`builder.ts:44`,
`:117`), sort direction is normalised to `ASC`/`DESC`, `LIMIT`/`OFFSET` are bound
params, and `tablePrefix` is only ever the hardcoded `"h"`.

### 1.2 Auth fails open when `API_KEY` is unset — **Critical**

`src/middleware/auth.ts:5-11` skips the check entirely when `API_KEY` is empty or
unset — the only signal is a `console.warn` at boot. Both `docker-compose.yaml:51` and
`deploy/mailgw/docker-compose.yaml:12` default it to empty, and `example.env` omits
`API_KEY` altogether, so anyone copying the example gets an unauthenticated service on a
published port. Only `deploy/core/docker-compose.yaml:42` uses the required `${API_KEY}`
form.

Should fail closed, or require an explicit opt-in such as `ALLOW_ANONYMOUS=1`. Related:
the comparison is a plain `!==` rather than `crypto.timingSafeEqual`, and the key is
snapshot at module load (`:3`), which is why `tests/auth.test.ts` has to use a dynamic
`import()`.

### 1.3 Three of four POST endpoints have no validation — **High**

Only `/api/delivery` validates (`src/routes/api.ts:10-21`, Zod).

| Endpoint | Validation |
|---|---|
| `POST /api/delivery` | Zod `schemaDelivery` |
| `POST /api/connection` | none — `toConnectionRow(body: any)` |
| `POST /api/queue` | none — `toTransactionRow(body: any)` |
| `POST /filter/md5` | none — only `Array.isArray` |

Consequences:

- A non-object body (`null`, `"str"`) throws a `TypeError` → 500 instead of 400.
- The `any` body defeats `strict`, so `ConnectionRow.remoteAddr: string` and friends are
  lying about nullability (`src/models/connection.ts:8`, `models/transaction.ts:4-9`).
- `dt` is unvalidated and fed to `FROM_UNIXTIME(${dt} / 1000)`; a string yields a MySQL
  type error → 500, an out-of-range value silently stores `NULL`.
- **`POST /filter/md5` fails open**: a non-array body returns `{action:"allow"}`
  (`src/routes/api.ts:91`) rather than 400 — the attachment blocklist silently permits.
- `src/query/hash.ts:46-56` writes a `HashLookups` row for *every* attachment including
  ones with no md5 (stored as `md5: ""`). A single POST with a 10k-element array becomes
  10k concurrent inserts (`Promise.all`, no batching, no cap).

### 1.4 Unbounded `limit` — **High**

`src/query/search.ts:71` is `q.limit ?? 100` with no clamp, and the webui proxy doesn't
bound it either (`webui-fastify/src/validation/search.ts:48` is `z.int().min(0)` with no
`.max()`). `{"limit":100000000}` attempts to serialise the entire table into JSON —
trivial memory exhaustion, especially with auth off. Deep `offset` is a cheaper variant
(MySQL scans the skipped rows). There is also no request body size limit and no
`Content-Type` check anywhere.

### 1.5 Malformed `q` shapes cause 500s — **Medium**

`{"search":{}}` → "not iterable" at `builder.ts:42`; `{"search":[null]}` → `item.value`
throws; `{"limit":"10"}` → a string bound to `LIMIT ?` → MySQL rejects. (`?q=null` was
in this set and is fixed as a side effect of §1.1.) Validating the whole payload with
Zod would close these together with §1.4.

### 1.6 Malformed JSON body returns 500, not 400 — **Medium**

`src/middleware/error.ts:7-10` catches the `await req.json()` failure and returns 500. No
POST route guards the parse.

### 1.7 Falsy search values are silently dropped — **Medium**

`src/query/builder.ts:43` — `if (!item.value && item.value !== 0) continue` drops
`false`, `""`, and `null`. So `tls = false`, `using_tls = false`, `remote_is_local =
false` and `auth = false` cannot be filtered: the condition is discarded and **all** rows
come back rather than an error or an empty set. Callers must know to send `0`.

The same silent-widening applies to an unknown field name (`:44`) and an unknown operator
(`:50`, no `default` case). For a security-log search UI, dropping a filter is the wrong
failure mode — it should error.

### 1.8 `withAuth` sits outside the error handler — **Low**

`src/index.ts:17` composes `withAuth(withErrorHandling(handler))`, so anything thrown in
`withAuth` escapes to Bun's default handler. Currently harmless, but inverted.

### 1.9 No secondary indexes anywhere — **High** (performance)

`migrations/001`–`014` create **zero** secondary indexes. The only keys are
`PRIMARY KEY (id)` plus `UNIQUE email` on `MailAddrs` and `Users`. Every searchable
column is a full scan. Worst offenders:

- `BlockMD5s.md5` (`007:3`) — queried on **every attachment of every message**
  (`models/blockmd5.ts:13`). Full table scan on the SMTP hot path.
- `Transaction.uuid` (`003:3`) — the join key in `search.ts:112`
  (`LEFT JOIN Transaction t ON t.uuid = h.txn_uuid`). Unindexed on both sides.
- `HashLookups.txn_uuid`, `md5`, `createdAt`; `Delivery.uuid, dt, sender, rcpt_domain,
  host, ip`; `Connection.uuid, dt, remoteAddr`; `Transaction.dt, sender, action` — all
  advertised as searchable in `docs/api.md`, none indexed.

`COUNT(*)` with a WHERE runs on every search request (`search.ts:49`, `:115`). These
tables also grow without bound — no retention or partitioning anywhere.

### 1.10 Column types that truncate or error — **Medium**

- `Delivery.response VARCHAR(255)` (`002:15`) and `rcpt_list VARCHAR(255)` (`002:6`,
  `003:8`) — long SMTP responses and multi-recipient lists are routine. Under
  `STRICT_TRANS_TABLES` (the MariaDB default) these **error**, turning a log write into a
  500. `Exceptions.info` already uses `TEXT`; these should too.
- `md5 VARCHAR(255)` (`007:3`, `008:4`) should be `CHAR(32)` — 8× the index size once an
  index is added.
- Booleans stored as `INT` rather than `TINYINT(1)`.
- No `ENGINE` / `DEFAULT CHARSET` / `COLLATE` on any table — inherits unpinned server
  defaults.
- No FKs or indexes on `Headers.mail_id`, `linkAddrTransactions.*`, `Relays.group_id`,
  `HashLookups.txn_uuid`.
- `Relays.auth_pass VARCHAR(255)` (`010:8`) — relay credentials in plaintext.

### 1.11 Schema/validation mismatches — **Low**

- `schemaDelivery` types `port` as a digit *string* (`validation/delivery.ts:20`) but
  `migrations/002:14` declares `INT`. Works via coercion.
- `.email()` on `rcpt_list` (`validation/delivery.ts:13`) means a multi-recipient list can
  never validate.
- `dt` unit ambiguity: the code divides by 1000 (ms) but `docs/api.md:135` documents
  seconds (`1717833600`). The documented example would store 1970-01-20.
- `dt DATETIME` has no fractional seconds and no timezone convention; `FROM_UNIXTIME`
  renders in the server's session tz, so the stored value is ambiguous.
- logservice is on zod v3 while webui-fastify is on `zod/v4` — worth aligning.

### 1.12 Migration runner — **Medium**

`src/dbmigrate.ts`: no advisory lock (two racing migrator containers both pass the
`applied` check, one fails on the `_migrations` UNIQUE and exits 1 — which deadlocks the
stack, since dependents gate on `service_completed_successfully`); no checksums, so
editing an applied migration in place is undetected; `db.unsafe(sql)` runs each file as
one statement, so a future multi-statement `.sql` will fail; no down/rollback path.

### 1.13 Dead code and Docker — **Low**

`src/models/mailaddr.ts` and `isMD5Blocked` (`models/blockmd5.ts:16-19`) are imported
nowhere. `src/models/transaction.ts:29-30` casts `as any` to read `rows.insertId`, whose
shape Bun's MySQL driver doesn't guarantee — latent, since the caller discards it.

`Dockerfile`: no `USER` (the `oven/bun` images run as root and ship an unused `bun`
user), no `HEALTHCHECK`, and `.env` is absent from `.dockerignore` (no leak today, since
only `src`/`migrations`/manifests are `COPY`'d — cheap insurance regardless).
`container-build.sh` and `container-push.sh` both run `bun pm version patch`, so
build-then-push double-bumps.

### 1.14 Test gaps — **Medium**

No coverage of `src/query/search.ts`, `src/routes/api.ts`, `src/middleware/error.ts`, or
any model. No test for the fail-open auth path (§1.2). `tests/auth.test.ts:9-18` spins up
a `Bun.serve` on :3001 that no test ever calls — dead scaffolding; every test invokes the
handler directly. The `tests/api/logservice.e2e.test.ts` auth block is
`describe.skipIf(!API_KEY)`, so in the default configuration it never runs.

## 2. mailgw (Haraka plugins)

### 2.1 `npFilter` silently disables `npConnection` — **High**

`plugins/npFilter.js:65` returns `next(OK)`. Haraka's dispatcher continues the chain only
on `CONT` — verified in `Haraka/plugins.js:464-470`, where any other retval sets
`hooks_to_run = []`. Since `config/plugins` lists `npFilter` before `npConnection`,
**`npConnection.hook_connect` never runs in production** and its local log file is never
written.

`hook_rcpt` (`:83`) does the same: it blanket-accepts every recipient and suppresses all
later `rcpt` hooks. The author evidently hesitated — `:84` has a commented-out
`// return next();`.

This is upstream of the "wire it up or clean it out" item in `mailgw/TODO.md`: the
cleanup decision doesn't matter while the hook is unreachable.

### 2.2 Duplicate `Connection` rows — **Medium**

`plugins/npData.js:9` posts connection info at `hook_data`, which fires once per
*transaction*, not once per connection. A pipelined client sending N messages on one
connection produces N inserts sharing the same `connection.uuid`, and logservice has no
unique key on it. The "no longer double-insert" comment in
`logservice/src/routes/api.ts:31` only addressed the other half of this.

### 2.3 `postWithLogging`'s error branch is unreachable — **High**

`httplog` (`plugins/functions.js:28-30`) already terminates with `.catch()`, so it never
rejects — it resolves `undefined`. The `.catch()` in `postWithLogging`
(`functions.js:113-125`) therefore **cannot fire in production**. A real connect failure
instead falls into the `else` at `:101` and is logged as *"HTTP Logfail, please review
logs on Logger side"* — pointing operators at the wrong system.

`tests/functions.test.js:243` passes only because it stubs `httplog` with a rejecting
fake: it tests a path that cannot occur.

Compounding it, there is **no `response.ok` check** anywhere, so an HTTP 500 from
logservice is recorded as `"status":500` and treated as success. No retry, no
dead-letter. Dropped events look healthy. `functions.js:120` also puts `httperror: error`
inside `JSON.stringify`, and an `Error` serialises to `{}` — message and stack are lost.

### 2.4 Attachment scanning fails open, inconsistently — **High**

(Currently latent — see the note below.)

- `plugins/AttachChecker.js:50` skips anything whose `contentDisposition` isn't
  `"attachment"`, so the MD5 blocklist is bypassed by sending the attachment `inline`.
- `:36` swallows network/JSON errors and fails **open**; `:77` swallows every
  `simpleParser` failure and fails **open with no log line at all**, so a malformed MIME
  message disables scanning invisibly.
- But `:35` does `action = res?.action`, so a 200 response without an `action` field
  yields `undefined`, and `npFilterAttach.js:42` then **DENYSOFTs** the mail. Fails open
  on error, closed on empty — inverted.
- No fetch timeout, and `hook_data_post` **is** `await`ed (`npFilterAttach.js:34`) — the
  one blocking call in the pipeline, unbounded.
- `npFilterAttach.js:7-9` hardcodes `http://localhost:3000` (already in
  `mailgw/TODO.md`), so all three URLs are wrong in the compose stack.

**Note:** this whole chain is presently **unreachable** — `config/plugins:8` disables it
as `#ngmFilterAttach`, which isn't even the plugin's filename (`npFilterAttach`). So the
`mailparser` dependency ships for dead code, and the duplicate-posting concern in
`TODO.md` is currently inert. Worth fixing the disposition bypass and the inverted
failure modes *before* re-enabling.

### 2.5 Unguarded config reads — **Medium**

`npData.js:6`, `npQueue.js:6`, `npLogDelivery.js:6` all call
`this.config.get("logging.json","json")` and immediately dereference the result. A
missing or malformed file makes `config.get` return null and the hook throws a
`TypeError` mid-transaction. `npFilter.js:52-57` handles exactly this case correctly for
its own config — the guard was never propagated. Since the config directory is
bind-mounted from the host, a missing file is realistic.

Same class in `npRoute.js:16-18, 86`: `rtable` is module-level and only assigned in
`register()`. If `getRelays`/`getRoutes` throw (missing `relays.json` →
`Object.values(null)` at `:98`), `rtable` stays `undefined` and every `hook_get_mx`
throws instead of deferring.

### 2.6 `RoutingTable` prototype-chain lookup — **Medium**

`plugins/RoutingTable.js:29` uses `relayname in this.relays`, which walks the prototype
chain. A route whose `relay` is `"constructor"`, `"toString"`, `"valueOf"` etc. passes the
existence check, and `:38` then hands a `Function` to Haraka as an MX. Should be
`Object.hasOwn`. Also `:32-35` uses `console.error` for a config error rather than the
Haraka logger, bypassing the configured log pipeline.

### 2.7 Divergent payloads for the same endpoint — **Medium**

`functions.buildTxnInfo` (used by `npQueue.js:10`) and `functions.log_transaction` (used
by `npFilterAttach.js:40`) both shape a transaction for `/api/queue` but emit different
fields:

- `buildTxnInfo` sends `rcpt_list` (a comma string) — what
  `logservice/src/routes/api.ts:69` actually reads.
- `log_transaction` sends raw `rcpt_to` (an array) instead, so `rcpt_list` maps to
  `null`. It also ships `headers: txn.header?.headers_decoded` — full decoded message
  headers (sender/recipient/subject PII) that logservice **discards**. PII over the wire
  with no consumer.
- `functions.js:159` posts `{status:"empty"}` with no uuid when the txn is missing,
  producing an all-null row.

### 2.8 Local logging is lossy and can corrupt — **Medium**

`functions.js:147-153` uses `fs.appendFile` with an empty `if (err) { }` — **every** disk
log error is swallowed. The `Dockerfile` never creates `log/` (only `plugins/`), so
without the host mount all local logging silently vanishes. The path is also
CWD-relative. Concurrent appends are separate open/write/close calls, so large payloads
can interleave and corrupt lines under load.

`functions.js:197-217` `censor()` returns the literal string `"[Unknown]"` for every value
past ~29 serialized entries, silently corrupting `toJson` output. It's copy-pasted
verbatim into `npFilter.js:103-129`.

### 2.9 Credentials in DEV logs — **Medium**

`npRoute.js:58-61` writes the full sender/rcpt/relay tuple — including the relay's
`auth_user`/`auth_pass` from `relays.json` — to `./log/ngmroute.log` in plaintext whenever
`MODE=DEV`, which is what `pnpm dev` sets. `npLogDelivery.js:13` writes the entire config
object (all logservice URLs) on **every** delivery.

### 2.10 Dead code and drift — **Low**

- `npConnection.isBlacklistedIP()` returns a hardcoded `false`; the `DENY` branch is
  unreachable (also in `TODO.md`).
- `functions.jsonlog` is never called **and** broken: it calls a bare `log(str)` that
  isn't defined in that module, so it would throw `ReferenceError`. The identical copy in
  `npFilter.js:125` works only because that file defines a local `log`.
- `functions.getDomain` is dead and duplicates `Route.getDomain`.
- `npFilterAttach.get_tmp_file` is never called and reads config that `register()` never
  loads. `npFilterAttach.js:12` has a stray `const plugin = this;`.
- `RoutingTable.js:1-2` exports are immediately overwritten by the class assignment;
  `:12-13` writes instance arrays onto the class as shared mutable statics that nothing
  reads.
- `functions.js:3` stamps `VERSION = "0.0.21"` into every log line while `package.json` is
  at `0.1.5` — the container scripts bump one and not the other.
- `functions.getAddrList` has no array guard unlike the hardened `getAddr`;
  `npLogDelivery.js:29` calls it with `hmail.todo.rcpt_to` unguarded, while `npRoute.js:49`
  guards the same field.
- `Route.js:16` — `addr.substring(addr.lastIndexOf("@") + 1)` returns the whole string as
  the "domain" when there's no `@`.
- `mailgw/package.json:19` declares the dependency as `"Haraka"` with a capital H — a
  portability trap on case-sensitive filesystems.

### 2.11 Test gaps — **Medium**

`AttachChecker`, `npFilterAttach`, `npConnection`, `npData`, `npQueue`, `npLogDelivery`
are entirely untested — every plugin that talks to logservice, plus the whole attachment
path. Nothing asserts the retval-stops-the-chain interaction of §2.1, which is why it
went unnoticed.

`tests/npFilter.test.js:7` and `tests/npRoute.test.js:6` `require("haraka-constants")`,
which is **not declared in `mailgw/package.json`**. It currently resolves to a leftover
root `node_modules/` directory from an old `bun install`; pnpm's strict layout does not
link it into `mailgw/node_modules`, so a clean checkout + `pnpm install` will fail these
two files. It belongs in `devDependencies`.

### 2.12 Dockerfile — **Medium**

Build toolchain (`python3 py3-pip make g++`, needed for `modern-syslog`) is installed and
never removed, so it stays in the runtime image. No `USER` — Haraka runs as root with no
privilege drop after binding port 25. `pnpm install --prod` has no `--frozen-lockfile`, so
builds are non-reproducible and `^3.3.1` floats — which makes copying `pnpm-lock.yaml`
pointless. The `allowBuilds` list is duplicated from `pnpm-workspace.yaml` (two sources of
truth). `CMD ["npm","run","start"]` puts npm at PID 1, which swallows `SIGTERM`, so
`docker stop` kills Haraka without a graceful SMTP shutdown and in-flight messages are
lost. No `HEALTHCHECK`.

## 3. webui-fastify

Worth stating plainly: **this package is in better shape than its `TODO.md` implies.**
Session TTL and server-side teardown, mass-assignment validation, `@fastify/helmet`,
login rate limiting, `setErrorHandler`, the proxy timeout, graceful shutdown, and the
`app.inject()` test suite are all genuinely done. Templates are also **XSS-clean** — there
is no unescaped pug interpolation (`!=` / `!{}`) anywhere, and `public/js/login.js` uses
`textContent` against a fixed message table rather than reflecting the `?msg=` param.

### 3.1 No CSRF protection on any state-changing route — **High**

`grep -ri csrf src/ templates/` returns nothing, and `@fastify/csrf-protection` is not a
dependency. Every mutation is a plain form POST with no token and no Origin/Referer check:

- `src/routes/config-relay.ts:13-30` — relay and relay-group create/edit/**delete**
- `src/routes/users.ts:11-17` — user create/edit/**delete**
- `src/app.ts:207, 218-219` — `POST /setup`, `POST /profile`

The mitigating factor is `sameSite: "strict"` (`src/auth/login.ts:31`), which does block
the classic cross-site form POST. But it's a single point of failure: it doesn't protect
against a same-site attacker (cookies are not origin-scoped, so any other app on the same
registrable domain qualifies), and it evaporates if the flag is ever relaxed for a
reverse-proxy or dev setup.

**This is not currently on the backlog** — unlike most items here, it's an unknown
unknown rather than a deferred decision. Related: `GET /logout` (`src/app.ts:202`) is a
state-changing GET.

### 3.2 Nullable columns round-trip as the string `"null"` — **High** (data corruption)

The edit forms interpolate with template literals instead of plain attribute assignment:

- `templates/pug/routing/relay-form.pug:12,15,18,21` — `value=\`${data.host}\`` etc.
- `templates/pug/routing/relaygrp-form.pug:11,14`
- `relay-delete.pug:11-20`, `relaygrp-delete.pug:10,13`, `users/delete.pug:12`

Every one of those columns is nullable (`db/schema.ts:35-36, 44-50`). `${null}`
stringifies to `"null"`, so editing a relay group whose `description` is NULL pre-fills
the input with the four characters `null` — and since the insert schema accepts any
string, **saving the form persists the literal string `"null"` into the DB**. Same for
`auth_user`.

Fix: use bare `value=data.description`, which pug omits for null/undefined.

### 3.3 `relay-delete.pug` renders a literal `undefined` — **Medium**

`src/controllers/CtrlRelay.ts:94` renders the view without passing `group_id`, which the
template uses twice: the hidden input gets `value="undefined"`
(`relay-delete.pug:8`) and the **Cancel button is a dead link** to
`/config/relaygrp/undefined` (`:25`). The delete itself still works — `deleteHandle`
re-reads `group_id` from the DB and ignores the body.

### 3.4 Missing-row guards are inconsistent — **Medium**

`CtrlUser` correctly redirects when the row is absent (`CtrlUser.ts:56-58, 95-97`). The
relay controllers don't: `CtrlRelay.ts:47-57` and `:85-94`, `CtrlRelayGroup.ts:37-46`,
`:68-77`, `:87-104`. With a stale or guessed id, `data` is `undefined` and the template
dereferences it immediately, throwing a `TypeError` that surfaces as a generic 500 page.
A non-numeric `:id` also yields `NaN` into the WHERE clause.

### 3.5 Audit log records no actor — **Medium**

`src/middleware/logger.ts:45` hardcodes `user: "-"`, even though `sessionEmail(request)`
(`src/auth/session.ts:10`) is available and the hook exists specifically to record config
mutations. An audit trail of mutations with no actor is of limited value — and `Logs.user`
exists for exactly this.

### 3.6 Audit inserts silently dropped for long headers — **Medium**

`src/middleware/logger.ts:35-46` writes `referer`, `userAgent`, `origin` and `query`
straight into `varchar(255)` columns (`db/schema.ts:57-65`). Real-world `User-Agent`
strings routinely exceed 255 chars, and `query` stores the *entire* `request.url` (not
just the query string) into a 255-char column while `url` gets 2048. Under strict mode
these inserts throw `ER_DATA_TOO_LONG`, and the fire-and-forget `.catch()` swallows them
into a stdout line — so audit rows are dropped for exactly the requests most likely to be
interesting. Truncate app-side or widen the columns.

### 3.7 Unbounded `limit`/`offset` in the proxy — **Medium**

`src/validation/search.ts:48` — see §1.4. Given the stated design goal of stripping and
bounding before forwarding, a `.max()` belongs here as well as upstream.

### 3.8 `uncaughtException` handler does not exit — **Medium**

`src/errhandler.ts:17-21` logs, persists to the DB, and returns — the process keeps
serving requests in an undefined state. Node's documented guidance is to log and exit.
Both handlers are also `async`, so the process could exit mid-`persist`.

### 3.9 Login policy caps passwords at 20 characters — **Low**

`src/validation/login.ts` applies `z.string().min(8).max(20)` on **login** as well as on
create. Any longer password (a password-manager default, a passphrase) can never be
entered, and the failure surfaces as `?msg=ValidationError`, indistinguishable from a
wrong password. bcrypt supports 72 bytes, so the ceiling is a self-imposed entropy cap
with no upside.

### 3.10 User-enumeration timing side channel — **Low**

`src/auth/util.ts:13-16` returns early without running bcrypt when the user doesn't
exist, so response timing differs measurably (bcrypt cost 10 vs. a DB miss). It also logs
`User not found: ${email}`, letting an unauthenticated caller write arbitrary strings to
server stdout. The HTTP responses are correctly identical.

### 3.11 Dead legacy pages served outside the auth gate — **Low**

`public/logs/{connection,delivery,lookups,queue}.html` and `public/js/log-*.js` are
referenced by nothing but are still served by `@fastify/static` at the root prefix
(`src/app.ts:171-175`), i.e. outside the auth gate. They fetch `/api/*`, which does
require a session, so an anonymous visitor just sees an empty grid — but they render
through vendored w2ui 1.5 (unmaintained since 2019, inconsistent HTML escaping in
`getCellHTML`), so an authenticated admin who loaded one would push SMTP-controlled
fields through it.

Deleting them also unblocks flipping CSP from `reportOnly` (`src/app.ts:93`) to enforcing
— the `unsafe-eval` concern noted in `TODO.md` applies only to w2ui/jQuery, and the live
pages have moved to AG Grid.

### 3.12 `tests/` is excluded from typecheck and lint — **Medium**

`tsconfig.json:29` and `biome.json:10` both scope to `src`/`db`/root `*.ts`, so the older
`tests/` directory is never checked. That hides a real type error:
`tests/checkSession.test.ts:20` writes a session without the required `expiresAt`
(`src/globals.ts:4-7`). It passes at runtime only by accident — `getSession` compares
`undefined <= Date.now()`, which is `false` via NaN, so such a session is treated as valid
forever.

`src/app.test.ts` (544 lines, 30 assertions, no DB or network) is the good suite; the
older `tests/*.ts` overlap it, are `any`-riddled, and use single quotes against the
project's Biome config. Either bring them under `tsconfig`/`biome` or fold their unique
coverage into `src/app.test.ts` and delete them.

### 3.13 In-memory sessions — **Low** (known)

`src/globals.ts:9` — per-process, so any scale-out or restart silently logs everyone out.
Fine for the current single-replica compose. Already tracked in `TODO.md`.
Related: logging in repeatedly leaves the previous session orphaned in the store until
the sweep runs.

## 4. Repo and infrastructure

### 4.1 Committed private key — **High**

`deploy/mailgw/settings/mine/config/tls_key.pem` is a tracked, unencrypted
`BEGIN PRIVATE KEY`; I confirmed it matches the paired `tls_cert.pem`. Impact is low —
it's an mkcert **development** cert (`O=mkcert development certificate`) that expired
2025-05-02 — but it is a real private key in git history and should be purged and rotated
on principle.

Alongside it: `deploy/mailgw/settings/mine/config/internalcmd_key` (a 64-hex-char
secret) and Mailtrap sandbox SMTP credentials in the same directory's `relays.json`.

Root cause: `certs/.gitignore` correctly blocks `*.pem`/`*.key`/`*.crt`, but the root
`.gitignore` does not, so anything outside `certs/` is unprotected. Adding those patterns
at the root is the cheap fix.

`mailgw/config/relays.json` commits placeholder `someuser`/`somepass` — not live
credentials, but it establishes the pattern of relay credentials living in a tracked file
with no `.example` suffix and no ignore rule, so the first real edit gets committed.

### 4.2 `docker-compose.yaml` defaults undermine the controls it configures — **High**

- `API_KEY: ${API_KEY:-}` (line 51) → logservice auth off (§1.2), while line 47 publishes
  it on `3000:3000`.
- `SIGN_COOKIE: ${SIGN_COOKIE:-changeme}` (line 70). `checkenv.ts:16` only checks
  *presence*, so `changeme` boots happily — the fallback defeats the entire point of the
  required-var guard. (Forgery is still bounded: the UUID must also exist in the
  in-memory store.)
- MariaDB published on `3306:3306` (line 21) with `MARIADB_ROOT_PASSWORD: P@ssw0rd` and
  `MARIADB_PASSWORD: P@ssw0rd` hardcoded — not even env-overridable, unlike the two
  above. The same literal repeats at lines 55, 75, 103, and in `example.env`.
- `webui-fastify/example.env:21` ships a real-looking `SIGN_COOKIE` value that the local
  `.env` uses verbatim — the example is being copy-pasted rather than replaced.

### 4.3 `deploy/core` sends the API key over plaintext HTTP — **Medium**

`deploy/core/docker-compose.yaml` publishes logservice on `3000` and
`deploy/core/deploy.sh` smoke-tests it over `http://`. Edge mailgw nodes POST to that
same plain-HTTP endpoint across hosts, so the shared `API_KEY` and all mail metadata
(senders, recipients, HELO names) cross the network in the clear. Needs TLS termination
or a private network.

### 4.4 CI is broken and gates nothing — **High**

`.github/workflows/publish.yml:35` runs `docker build .` from the repo root, but **there
is no root `Dockerfile`** — it moved to `mailgw/Dockerfile` and the workflow was never
updated, so the published-image job cannot succeed. The Node setup and `pnpm install`
steps are commented out (lines 20-31), no tests run anywhere, and neither `logservice`
nor `webui-fastify` is built or tested.

There is no lint / typecheck / test gate on any package, on any branch. Both
`webui-fastify/TODO.md` and this review assume `pnpm typecheck` + `pnpm check` +
`bun test` should gate merges; nothing does.

### 4.5 Documentation drift — **Low**

- `CLAUDE.md` and `AGENTS.md:32` both state the Haraka runtime config files are "not in
  the repo", but all six *are* tracked under `mailgw/config/`. They are also **not copied
  into the image** (`mailgw/Dockerfile:13-15` copies only manifests and `plugins/`) —
  runtime config comes from the `/opt/mailgw/config` bind mount. So the committed copies
  are decorative, nothing verifies they match production, and drift is undetectable.
- `mailgw/config/logging.json` points at `http://logservice:3000`, but the compose service
  is named `dev-logservice` with no `logservice` network alias — so unless the
  host-mounted copy differs, DNS resolution fails and every log POST silently errors out
  (and, per §2.3, gets mislabelled "HTTP Logfail").
- `logservice/docs/api.md:135` documents `dt` in seconds while the code expects
  milliseconds (§1.11).

`AGENTS.md` is otherwise accurate and current — I checked its claims against the code.
